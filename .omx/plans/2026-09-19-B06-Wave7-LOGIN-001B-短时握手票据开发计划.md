## 1. 勘查结论（2026-09-19，main 76f78eba）

- WS 认证链：`/infra/ws` 由 starter `WebSocketAuthorizeRequestsCustomizer` 在过滤器链**放行**，认证在握手拦截器 `LoginUserHandshakeInterceptor`（读 SecurityContext；SecurityContext 由 `TokenAuthenticationFilter` 经 SEC-003 `obtainAuthorization`（Header>Parameter）填充）。gate 翻 false 后 `?token=<refreshToken>` 不再建立 SecurityContext → 握手被拒——**迁移窗口即本卡**。
- 握手拦截器装配：starter `webSocketConfigurer` 注入 `HandshakeInterceptor[]`（容器内全部 bean），故 system 模块注册的新拦截器 bean 会被自动带上；顺序用 `@Order` 控制。
- `WebSocketFrameworkUtils.ATTRIBUTE_LOGIN_USER="LOGIN_USER"`（attributes 键）；`LoginUserHandshakeInterceptor` 现行：无 SecurityContext 用户即 `return false`——须加「attributes 已带 LOGIN_USER → 透传」三行（starter 唯一改动）。

## 2. 设计决策

1. **票据形态**：一次性短时票据（UUID），Redis `oauth2_ws_ticket:{ticket}` → JSON {userId,userType,tenantId}，TTL 默认 60s（`zszj.security.ws-ticket.ttl-seconds`）；消费用 `getAndDelete` 原子取删（一次性、防重放）。
2. **发放**：`OAuth2WsTicketService.issue(LoginUser)` ← `POST /system/auth/ws-ticket`（登录态，SecurityContext 主体；ADMIN/MEMBER 同链两端通用）。
3. **消费（握手）**：新增 `OAuth2WsTicketHandshakeInterceptor`（system 模块，`@Order` 最高先跑）：有 `?ticket=` → consume → LoginUser 写入 attributes（ATTRIBUTE_LOGIN_USER）；无 ticket 参数 → 直接放行交由既有链（gate=false 下旧 token 参数自然被拒，行为兜底不变）。
4. **starter 三行改动**：`LoginUserHandshakeInterceptor` 顶部「attributes 已带 LOGIN_USER → return true」（票据路径透传；SecurityContext 路径行为不变）。
5. **gate 翻转**：删 application.yaml L324-326 注释+键（代码默认 false 生效）；`removeAccessToken` 不再受合成令牌阻碍；LOGIN-001 @PostConstruct WARN 随 false 静默。
6. **前端**：连接前以 Authorization 头调票据端点取票 → `?ticket=`；取票失败不连接并退避重试；重连重新取票（一次性语义）。
