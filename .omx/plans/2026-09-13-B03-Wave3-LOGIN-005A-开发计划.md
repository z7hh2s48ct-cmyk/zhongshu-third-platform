## 任务卡（docs/05 ZS-LOGIN-005 主卡 B03 部分）

- 调整：定义事务提交、缓存失效、权威撤销状态和失败补偿顺序；B03 先完成权威校验与失效安全闭环；不把 Redis 操作视为被 PG 自动回滚；无需 Outbox（B05 由 ZS-JOB-002 扩展可靠补偿）。
- 验收（§16.1）：PG/Redis 故障和并发回填不恢复撤销会话；失败有告警和可重放修复证据。

## 设计（B03.A 安全闭环三层）

1. **DB 权威校验（幽灵凭据根本闭环）**：`checkAccessToken` 缓存命中后回源 DB 校验行存在且未逻辑删除（普通令牌查 access 表；gate=true 的合成令牌查 refresh 表），不存在即「已撤销」——自愈 evict 缓存 + 401；DB 查询异常失败关闭（安全默认）并告警。Redis 从「权威」降级为「加速」，撤销路径 Redis 失效失败不再产生可用幽灵。
2. **提交后缓存失效（afterCommit/回滚补偿）**：撤销类失效动作（墓碑+删缓存+代际键）注册到 `afterCommit`（提交后执行）；事务回滚时同样执行失效（回滚补偿——缓存 miss 回源重建，安全方向）；无事务上下文时立即执行（兼容测试/自调用）。新建类动作（新访问令牌写缓存）仅在提交后发布，回滚时确保不残留（堵「缓存成功而事务回滚」的幽灵新令牌）。
3. **失败告警与可重放证据**：Redis 动作失败不阻断 DB 提交，WARN 结构化日志（脱敏键清单 + 引导：DB 权威校验自愈 evict 即修复路径），登记 B05 重放入口。

## 测试计划（TDD RED 先行）

- `checkAccessToken_cachedButRevokedInDb_rejectsAndEvicts`（真实 Redis+DB）：缓存命中但 DB 行已删 → 401 且缓存被清。
- `createAccessToken_rolledBackTx_noGhostCacheEntry`：事务回滚后新令牌不得残留在 Redis（修复前 RED）。
- `createAccessToken_committedTx_cachePublished`：提交后缓存正常发布（不误伤可用性）。
- `removeAccessToken_redisFailure_dbStillAuthoritative`（mock）：Redis 动作抛异常 → 撤销仍成功 + 告警。
- 既有墓碑/锁序/孤立凭据测试全量保持绿。
