### 2.2 失败测试设计（RED）

新增/扩展测试（monitor starter 若无 src/test 则新建，或落 web starter 复用 SEC-012.A 夹具）：

1. `TracerUtilsFallbackTest`（common）：无有效 Span 时 `getTraceId()`（或新增 `getCorrelationId()`）**返回非空、有界（长度上限）、格式合法**的关联 ID；连续调用同一请求上下文内稳定、不同请求不串号。RED：现状返回空串。
2. `TraceFilterTest`（monitor/web）：①无 OTel 时响应头 `trace-id` 非空且为 fallback 关联 ID；②外部传入合法 `trace-id` 头按信任边界处理（复用或拒绝承载权限，见 2.3）；③外部传入**畸形/超长** trace-id 被拒或替换为服务端生成值，不回显；④过滤器链早退（异常）时响应头仍有关联 ID。RED：现状空串 + 无外部校验。
3. **异步传播**：`Callable`/`@Async` 端点二次派发时关联 ID 不丢失、不串号（复用 SEC-002 已建的异步端点夹具 `TestControllers` Callable）。
4. **错误关联一致性**：认证失败/参数失败/系统失败三条错误路径，`GlobalExceptionHandler` 输出的错误日志与响应体携带**同一关联 ID**，前端可据此定位服务端日志。
5. **CORS 暴露确认**（不重做，仅回归）：跨域预检 `Access-Control-Expose-Headers` 含 `trace-id`（断言 SEC-004 预置未被破坏）。

### 2.3 最小实现要点（GREEN）

- **fallback 关联 ID 生成**：在 `TracerUtils` 新增「有 OTel 用 traceId、无则用请求作用域 fallback」的统一入口（如 `getCorrelationId()`），fallback 为**有界、随机、不可承载权限**的 ID（如 128-bit 十六进制或 UUID 去横线），**明确区分「关联 ID」与「分布式 Trace」**（javadoc + 文档记录）。保留 `getTraceId()` 语义不变（仍返回 OTel traceId 或空），避免破坏既有消费方；关联 ID 走新方法或请求属性。
- **请求作用域存储**：fallback ID 绑定到当前请求（`HttpServletRequest` attribute 或 ThreadLocal + 异步 TaskDecorator 传播），过滤器早退/异常仍能取到；线程复用（连接池）时**每请求重置**，杜绝串号。
- **外部传入信任边界**：`TraceFilter` 读取外部 `trace-id` 头时**校验格式（长度/字符集）**，合法则可作关联 ID 复用（便于端到端串联），但**绝不作为授权/身份凭据**；畸形/超长则忽略并用服务端生成值，不回显攻击者可控原文。
- **统一写点**：响应头（TraceFilter）、访问日志（ApiAccessLogFilter，若需）、错误日志与错误响应体（GlobalExceptionHandler）共用同一关联 ID 取值入口。

### 3.2 失败测试设计（RED）——「先用并发测试复现再修复」（docs/05 L439）

新增 `OAuth2TokenServiceImplRefreshConcurrencyTest`（system src/test，H2 `BaseDbUnitTest` 或独立 PG 夹具 + 真 Redis/jedismock）：

1. **并发刷新复现**：同一 refreshToken，N 个线程（如 8）并发调 `refreshAccessToken`——RED 断言「最终有效 access token 数 == 1（或按合同的受控代际数）」，现状会产生多个（>1）→ 复现失败。
2. **重放拒绝/受控幂等**：同一 refreshToken 连续两次刷新，第二次按合同「拒绝（重放）或返回同一代际结果（受控幂等）」，不得产生两个独立有效会话。
3. **退出后晚到刷新不复活**：线程 A `removeAccessToken`（退出）与线程 B `refreshAccessToken`（晚到）并发——退出完成后 B 不得复活会话（断言最终无有效 access/refresh）。
4. **会话代际可定位**：刷新产生新代际时保留可定位标识（如 refresh token 版本号/代际序号），便于审计与「保留可定位的会话代际」（docs/05 L438）。
5. **网络重试按合同**：模拟客户端重试（同 refreshToken 短时间内重复），服务端串行化，不产生失控会话。

### 3.3 最小实现要点（GREEN）

- **串行化同一会话刷新**：`refreshAccessToken` 对 refreshTokenDO 加**行锁**（`selectByRefreshTokenForUpdate`，Mapper 加 `FOR UPDATE`）或**条件领取**（乐观锁：`UPDATE ... SET version=version+1 WHERE refresh_token=? AND version=?`，影响行数 0 即并发冲突拒绝）。二选一，优先行锁（PG 原生支持，语义清晰）。
- **轮换 vs 受控幂等合同**：明确本底座采用「刷新轮换 refresh token（旧 refresh 失效）」还是「沿用 + 代际号 + 重放拒绝」。**决策：采用沿用原 refresh + 会话代际号 + 重放检测**（最小改动、不破坏 LOGIN-001 门控与前端刷新契约），代际号存于 refresh token 记录或 access token 关联，重放（旧代际）拒绝。若产品要求轮换则记为 LOGIN-002 扩展/B 卡。
- **刷新与退出竞态**：行锁串行化后，退出（removeAccessToken）删 refresh 与刷新在同一锁序下，晚到刷新读不到 refresh（已删）→ 抛「刷新令牌已过期/不存在」，不复活。
- **错误码**：如需新增「刷新令牌重放/会话代际冲突」码，落 system `ErrorCodeConstants.java` OAUTH2 段（与 LOGIN-004 串行，同分支顺序演进）。

### 5.4 正反向验收判据（对齐 docs/05 L584）

- **正向**：合同内合法值创建/更新成功；热生效项消费端读到新值、需重启项行为符合标注；敏感参数更新审计只含脱敏摘要。
