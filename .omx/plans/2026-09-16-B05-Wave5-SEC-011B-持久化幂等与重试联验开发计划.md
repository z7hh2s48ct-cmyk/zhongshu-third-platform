## 2. 设计决策（收口论证）

1. **持久化幂等 = DB 单层，不叠 Redis 窗口锁**：`@Idempotent(persistent=true)` 走 DB 唯一约束单层串行化，Redis 与 DB 双层竞态在结构上不存在（退出条件「DB 唯一约束兜底，防双层竞态」以更强形式满足：唯一约束是**唯一**裁决层）。非 persistent 模式行为完全不变。
2. **SPI 分层**：protection starter 新增 `PersistentIdempotentStore`（接口）+ `PersistentIdempotentRecord`（POJO）+ `PersistentIdempotentStatus`（RUNNING/SUCCESS/FAILED 枚举）；`zszj-module-infra` 新增 `JdbcPersistentIdempotentStore`（@Repository + JdbcTemplate + 循 `OutboxTransactions` 的同源配对 MANDATORY 模板）。protection→infra 零依赖；切面经 `ObjectProvider<PersistentIdempotentStore>` 懒解析，**persistent=true 而容器无 store bean → 启动后首次调用即 fail-fast**（IllegalStateException，不静默降级）。
3. **事务原子性 = MANDATORY 参与调用方事务**（循 JOB-002 先例）：INSERT RUNNING → `proceed()` 业务 → markSuccess（或失败 DELETE/markFailed）全部加入调用方在同一数据源的事务，**一次提交同生共死**：提交前崩溃 → 记录不存在，重放安全重执行（业务未发生）；提交后崩溃/丢响应 → 记录 SUCCESS+快照，重放复用。无「业务已提交但记录 RUNNING」悬挂窗口。**使用约束**：注解必须落在事务内 service 方法（无事务 → MANDATORY 抛 IllegalTransactionStateException，fail-closed 拒绝，不另开事务自提交）。
4. **PG 唯一冲突不毒化事务**：抢锁 INSERT 用 `INSERT ... ON CONFLICT (idempotent_key) DO NOTHING`（PG 专有 unique violation 会 abort 整个事务，导致败者连 SELECT 都发不出；ON CONFLICT 不 abort，败者可继续 findByKey 分类「重复/冲突/复用」）。先 SELECT 快路径（顺序重放不产生写、不触发冲突），并发竞态败者经 DO NOTHING + 二次 SELECT 分类。H2（MODE=MYSQL，2.x）支持 ON CONFLICT 标准文法，实现时以 store 测试实证。
5. **Key/Value 切分（收编 .A P2-1 + REC-2）**：`DefaultIdempotentKeyResolver`/`UserIdempotentKeyResolver` 的 Key **去掉 argsStr**（Key = 稳定短键：method+作用域），入参以**未截断脱敏表示**的 MD5 全量摘要存 Value/`request_digest` 参与比对——冲突检测在默认路径变为可达（同键异参 → 冲突）。摘要新增 `LogSanitizeUtils.sanitizeArgsUntruncated`（`sanitizeArgs` 改为 truncate(内部复用)，零行为变化）。**边界如实声明**：同主体同方法 1 秒窗口内连发不同参数的合法调用会被判冲突（这正是主卡「同键不同参数明确冲突」合同；生产接入时可用 Expression 解析器自定业务键或调大 window 语义自担）。
6. **持久化模式强制登录主体（收口 `.A` collapse 危险语义）**：持久化记录携带结果快照 → 匿名/无上下文塌缩即跨主体结果重放。切面 persistent 分支要求 `WebFrameworkUtils.getLoginUserId(request) != null`，否则 fail-closed 拒绝（500 语义的使用错误 + ERROR 日志）；主体因子（tenant/userId/userType）强制并入 storeKey（`md5(resolverKey + ":" + tenant + ":" + userId + ":" + userType)`，`md5` 全量哈希无截断碰撞）→ 不同主体永不共用持久化键，同时消除 Expression 解析器无主体作用域在持久化路径的风险。**持久化键一律 `md5` 定长 32**，落 `varchar(64)`，无 2048 截断问题。
7. **结果快照与复用边界**：`proceed()` 返回值经 `JsonUtils.toJsonString` 快照入 `result_snapshot`（text）；重放（SUCCESS + 快照非空 + 摘要相等）→ `JsonUtils.parseObject(snapshot, method.getGenericReturnType())` 返回原结果（HTTP JSON 形状不变；Java 直调泛型元素退化为 LinkedHashMap 的边界如实登记）。序列化失败 → markSuccess(快照=null)（业务不因快照失败而失败）→ 重放退化为**状态级复用**（900 重复拒绝）；快照损坏同理降级 900，**绝不重执行业务**。RUNNING → 900（处理中，不重复写）；FAILED（deleteKeyWhenException=false 时保留）→ 900；摘要不等 → 900+冲突文案。`deleteKeyWhenException=true`（默认）→ 失败 DELETE 记录（与 .A Redis 语义一致：失败可重试）。
8. **重试重检授权（方法安全次序合同）**：`IdempotentAspect` 显式 `@Order(Ordered.LOWEST_PRECEDENCE)` + 合同测试证明 Spring Security 方法安全拦截器（@PreAuthorize，order≈400）**先于**幂等切面执行——撤权/无权主体重放同键请求 → AccessDeniedException，幂等快照**不被返回**、业务不执行；同键跨主体（均合法）→ 主体因子进 Key → 不同键 → 各自执行，不误用他人结果。幂等切面自身不读不缓存任何权限判定。
9. **错误码**：复用 `GlobalErrorCodeConstants.REPEATED_REQUESTS`（900），零新错误码。
10. **P2-2（裸 expression key 日志）**：读回摘要失败分支 `log.warn` 改携 `SecureUtil.md5(key)` 指纹（可关联、不可逆），不落原值；该修复同样使持久化路径天然不落敏感键（storeKey 即 md5）。

## 5. 登记边界（红线，收口如实声明）

1. 快照按**声明返回类型**反序列化：HTTP JSON 形状不变；Java 直调方泛型元素类型保真不承诺（退化 LinkedHashMap）。
2. 业务异常不快照：失败重试语义由 `deleteKeyWhenException` 决定（默认删记录可重试）；FAILED 保留路径重放恒 900，不区分「原异常」。
3. 持久化幂等要求：事务内 service 方法 + 登录主体；不满足即 fail-closed 拒绝（不做匿名持久化幂等，无跨主体回放）。
4. 记录保留期/清理、容量与性能标定不在本卡（归 B11/WP-19 实测）；**不声称生产级吞吐/时延**。
5. 跨实例时钟：complete_time 应用侧时钟（循 outbox 单一时钟源惯例），不做跨实例时钟假设；状态机不依赖时钟（无 RUNNING 过期接管——悬挂 RUNNING 只可能来自非事务误用，MANDATORY 已在结构上排除）。
6. Redis 故障语义（Redis 模式）维持 .A 原状（fail-closed 拒绝 + 降级文案），本卡不改其承诺。
7. 主卡 ZS-SEC-011 维持「开发中」：.B 交付≠主卡已验收；HTTP 全链重放联验的端到端面归 ZS-SEC-012 既有入口。
