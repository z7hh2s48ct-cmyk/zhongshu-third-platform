### 卡片验收标准 → 落点映射

1. **转岗不重写已发生业务的责任历史** → `transferMembership` 仅改 `organizationId` + 追加流水；新增测试断言历史行不被 UPDATE、既有业务责任归属不被触碰。
2. **停用/离职及时失权** → `changeStatus(→SUSPENDED/TERMINATED/EXPIRED)` 联动 `OAuth2TokenService.removeAccessToken(userId, ADMIN)`（复用 LOGIN-003 撤销链，`@Lazy` 注入避免循环依赖，镜像 `AdminUserServiceImpl.invalidateUserSessions`）。
3. **恢复不意外恢复旧越界授权** → `changeStatus(→ACTIVE)`（RESUME）**不**主动复活任何令牌；已撤销会话保持撤销，重新登录时经 `MembershipContextResolver` fail-closed 重解析（有效期/组织开启重新校验），旧越界上下文不自动回归。
4. **迁移有前后核对和恢复方案，不执行未经批准的账号合并** → 扩展 PG 验证：`count(有效 dept 且组织匹配的 users) == count(回填 memberships)`；恢复方案（回滚 SQL + 校验脚本）落 `docs/`；沿用 IAM-002「按 user_id 逐一驱动、绝不按 username/mobile 聚合」不合并原则。

## 二、关键设计决策（待用户确认）

### D1：失权触发范围（多任职账号语义）

`MembershipContextResolver` 仅依据**默认任职（primary）**解析服务端组织上下文并签名进 token。故：

- **方案 B（推荐，精确）**：仅当①被变更任职是该账号的 primary，或②变更后该账号已无任何 ACTIVE 任职时，才撤销全部会话。理由：token 上下文只由 primary 决定；停用一条非 primary 的次级任职不影响已签发上下文，无需强制全端下线。存量迁移账号每人恰一条 primary，常见路径下 B 与 A 行为一致。
- **方案 A（宽泛）**：任何任职 → SUSPENDED/TERMINATED/EXPIRED 都撤销该用户全部会话。更简单但会因次级任职停用而过度中断。

### D2：审计口径

新增 `LogRecordConstants`：`SYSTEM_MEMBERSHIP_TYPE = "SYSTEM 任职"`，子类型覆盖 入职/转岗/状态流转（停用/复职/离职/过期）。`bizNo = "{{#membershipId}}"`，success 文案含组织/状态语义。审计与 `system_membership_history` 流水互补：流水承载结构化历史归属（只增不改、业务责任溯源），@LogRecord 承载操作日志（操作者/时间/trace-id，与 LOGIN-003 撤销日志同 trace 关联）。
