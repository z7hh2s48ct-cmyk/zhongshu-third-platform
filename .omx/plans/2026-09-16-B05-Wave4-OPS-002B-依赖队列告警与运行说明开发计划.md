### 0.3 关键设计决策（勘查发现，执行前须知）

1. **积压绝不进 liveness（反重启风暴铁律）**：`OutboxQueueHealthIndicator` 汇入聚合 `/actuator/health` 与 `monitoring` 组，**绝不加入 `management.endpoint.health.group.liveness.include`**。理由：liveness 语义 = 「进程是否存活/是否需重启」；队列积压是**业务负载信号**，进程仍健康——若积压使 liveness DOWN，compose healthcheck（探 `/actuator/health/liveness`）会判定容器不健康并**重启**，重启不消除积压 → **重启风暴**。测试断言：`monitoring` 组含 `outboxQueue`、liveness 组不含（配置层断言 + 文档明示）。
2. **依赖故障 vs 队列积压的健康语义分离**：**依赖故障（DB/Redis DOWN）** → 应用确实无法正常服务，`db`/`redis` 指示器 DOWN 汇入聚合 health（Spring Boot 自动装配），readiness 可反映；**队列积压** → `outboxQueue` 指示器降级但**不杀 liveness**。二者都在 `monitoring` 组「被发现」，但只有依赖故障影响服务可用性判定。
3. **失败不静默的三层含义（退出条件核心）**：①**探针异常不吞**——`snapshot()` 抛出（DB 不可用等）→ ERROR 日志明示 + `Health.down()`，**绝不 catch 后返回 UP/空**（那正是「静默」）；②**越阈必告警**——`breaches` 非空 → 结构化日志按严重度输出（不再仅 JOB-004 的 `log.warn` 单点，而是分级 + 周期）；③**调度线程不被击穿**——探针 try/catch 隔离，单轮失败不终止后续轮次（否则一次异常后永久静默）。
4. **复用 JOB-004 越阈码，不新造监测逻辑**：本卡**不重算**积压/DEAD/失败率（JOB-004 `OutboxHealthMonitorImpl.evaluateBreaches` 已是单一真源）；探针与指示器都只**消费** `snapshot().getBreaches()`，按码分级/呈现。越阈码集合固定 6 种（§地面真相），运行说明逐码给响应动作。
5. **严重度分级映射**：`PENDING_BACKLOG_CRITICAL` / `DEAD_EVENTS_PRESENT` / `STALE_LEASE_PRESENT` → **ERROR**（需人工介入：CRITICAL 积压、DEAD 需恢复控制台处置、租约停摆征兆）；`PENDING_BACKLOG_WARN` / `LONGEST_WAIT_WARN` / `FAILURE_RATE_WARN` → **WARN**（预警，观察/排查）。`HealthIndicator` 降级态可携最高严重度。分级依据 = JOB-004 码语义（CRITICAL/PRESENT 为「存在即告警」硬阈，WARN 为软阈）。
6. **系统级不加租户过滤**：探针与指示器都是**系统级运维视图**（循 `OutboxHealthMonitorImpl` L16「不加租户过滤，服务统一告警诉求」）——`@Scheduled` 无请求上下文、`HealthIndicator` 无租户，二者天然系统级；**不调 `TenantContextHolder`**（与 JOB-004 恢复服务的租户过滤入口分工）。
7. **阈值/间隔保守占位（反模式红线）**：`alert.interval-ms` 与既有 `infra.outbox.health.*` 阈值同为**保守占位，待 WP-19 实测回填**；**禁止在计划/代码注释/运行说明编造「支持 N 万 TPS」「N 秒内告警达生产级」类未经实测断言**（循 JOB-004 铁律 8 + 验收④）。运行说明明示占位状态。
8. **配置门控使单测确定**：`OutboxHealthAlertScheduler` 用 `@ConditionalOnProperty(prefix="infra.outbox.health.alert", name="enabled", havingValue="true")`（或等价）——单测可显式开/关，避免 `@Scheduled` 在无关测试中意外触发；指示器 bean 无条件注册（health 端点按需拉取，不自动跑）。
9. **主树中文路径**：`mvn`/`java` 无法经 PATH 查找，须绝对路径调用（§1.2 铁律 5）；worktree（ASCII junction 路径）内可正常 `mvn`。

### 2.1 告警探针 `OutboxHealthAlertScheduler`（infra `framework/outbox/health/`）

```java
@Component
@ConditionalOnProperty(prefix = "infra.outbox.health.alert", name = "enabled", havingValue = "true")
@Slf4j
public class OutboxHealthAlertScheduler {

    private final OutboxHealthMonitor monitor;

    public OutboxHealthAlertScheduler(OutboxHealthMonitor monitor) { this.monitor = monitor; }

    // 间隔保守占位（默认 60s），待 WP-19 实测回填；fixedRateString 从配置解析
    @Scheduled(fixedRateString = "${infra.outbox.health.alert.interval-ms:60000}")
    public void probe() {
        OutboxHealthMetrics metrics;
        try {
            metrics = monitor.snapshot();
        } catch (RuntimeException ex) {
            // 失败不静默（铁律 10）：探针异常明示 ERROR，不吞、不返回健康、不击穿调度线程
            log.error("[probe][Outbox 健康监测探针失败，依赖可能不可用 errorClass={}]",
                    ex.getClass().getName(), ex);
            return;
        }
        List<String> breaches = metrics.getBreaches();
        if (breaches == null || breaches.isEmpty()) {
            return; // 健康，无告警（或 DEBUG）
        }
        // 按严重度分级（§0.3-5）：CRITICAL/DEAD/STALE → ERROR；WARN 类 → WARN
        if (hasCritical(breaches)) {
            log.error("[probe][Outbox 队列告警(严重) breaches={} pendingBacklog={} deadCount={} "
                    + "longestWaitSeconds={} failureRatePercent={} staleLeaseCount={}]",
                    breaches, metrics.getPendingBacklog(), metrics.getDeadCount(),
                    metrics.getLongestWaitSeconds(), metrics.getFailureRatePercent(),
                    metrics.getStaleLeaseCount());
        } else {
            log.warn("[probe][Outbox 队列告警(预警) breaches={} pendingBacklog={} deadCount={} "
                    + "longestWaitSeconds={} failureRatePercent={} staleLeaseCount={}]",
                    breaches, metrics.getPendingBacklog(), metrics.getDeadCount(),
                    metrics.getLongestWaitSeconds(), metrics.getFailureRatePercent(),
                    metrics.getStaleLeaseCount());
        }
    }

    private static final Set<String> CRITICAL_CODES = Set.of(
            "PENDING_BACKLOG_CRITICAL", "DEAD_EVENTS_PRESENT", "STALE_LEASE_PRESENT");

    private boolean hasCritical(List<String> breaches) {
        return breaches.stream().anyMatch(CRITICAL_CODES::contains);
    }
}
```

> 设计要点：①`@ConditionalOnProperty` 门控（§0.3-8，单测可控）②探针异常 ERROR 明示并 `return`（不吞不击穿，铁律 10）③分级复用 JOB-004 码（§0.3-4/5，不重算）④系统级无租户（§0.3-6）⑤间隔占位待实测（§0.3-7）。严重度集合以 JOB-004 `evaluateBreaches` 码语义为单一真源。

### 2.2 队列健康指示器 `OutboxQueueHealthIndicator`（infra `framework/outbox/health/`）

```java
@Component("outboxQueue")   // 健康贡献者名 outboxQueue（供 monitoring 组 include）
public class OutboxQueueHealthIndicator implements HealthIndicator {

    private final OutboxHealthMonitor monitor;

    public OutboxQueueHealthIndicator(OutboxHealthMonitor monitor) { this.monitor = monitor; }

    @Override
    public Health health() {
        OutboxHealthMetrics metrics;
        try {
            metrics = monitor.snapshot();
        } catch (RuntimeException ex) {
            // 依赖故障不静默为 UP（铁律 10）
            return Health.down().withDetail("reason", "MONITOR_PROBE_FAILED")
                    .withDetail("errorClass", ex.getClass().getName()).build();
        }
        List<String> breaches = metrics.getBreaches();
        Health.Builder builder = (breaches == null || breaches.isEmpty()) ? Health.up() : Health.down();
        return builder
                .withDetail("pendingBacklog", metrics.getPendingBacklog())
                .withDetail("deadCount", metrics.getDeadCount())
                .withDetail("longestWaitSeconds", metrics.getLongestWaitSeconds())
                .withDetail("failureRatePercent", metrics.getFailureRatePercent())
                .withDetail("staleLeaseCount", metrics.getStaleLeaseCount())
                .withDetail("breaches", breaches)
                .build();
    }
}
```

> 设计要点：①bean 名 `outboxQueue` → 汇入聚合 health + 可被 `monitoring` 组 include（§0.3-1）②**不进 liveness**（默认即不进，配置层再显式排除并注释）③越阈 → `Health.down()` 携 breach 详情（「被发现」）④探针失败 → `down()` + `MONITOR_PROBE_FAILED`（不静默 UP，铁律 10）⑤details **不含 payload/异常原文**（循 JOB-004 脱敏红线，仅指标值 + 码 + 异常类名）。降级用 `down()` 还是自定义 `status("BREACH")` 收口定夺——`down()` 更通用（任意监控识别），但会使聚合 health DOWN；若担心聚合 DOWN 影响 readiness，可改自定义状态 + `monitoring` 组独立呈现，测试断言随之调整。
