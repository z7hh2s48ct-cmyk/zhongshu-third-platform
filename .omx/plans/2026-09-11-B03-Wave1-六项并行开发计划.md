# B03 Wave 1 六项并行开发计划

> **致执行者（For agentic workers）：** 本计划按任务逐一执行，每个任务用复选框（`- [ ]`）跟踪。推荐用 subagent-driven-development（每个 worktree 派一个新子代理、任务间两阶段评审）；或 executing-plans（本会话内分批执行 + 检查点）。**代码在各自 worktree 并行，文档只在主树串行同步**——这是本计划的铁律，任何子代理不得在 worktree 内改 `docs/`。

**目标（Goal）：** 在 B03 批次内，把 6 个前置已满足的安全/登录/配置/组织任务（ZS-SEC-004、ZS-SEC-010、ZS-SEC-011.A、ZS-CFG-001.B、ZS-LOGIN-001、ZS-IAM-003）通过 5 个物理隔离的 git worktree 并行推进到「待验收」，每项走通「失败测试→最小实现→模块 mvn→本地门禁→codex 评审闭环→合并→文档串行同步」全周期。

**架构（Architecture）：** 按**文件所有权**将 6 任务映射到 5 个 worktree——文件集互不相交的任务真并行；唯一共享文件（`zszj-module-system` 的 `ErrorCodeConstants.java`，被 LOGIN-001 与 IAM-003 同时触碰）的两任务收敛到同一 worktree 内**串行**，从根上消除跨树合并冲突。主树 `main` 始终保持干净、专用于串行合并 + 文档同步 + 门禁复验。

**技术栈（Tech Stack）：** Spring Boot 3 + JDK 17 + Maven（`tools/` 自引导 Temurin 17.0.20.1 + Maven 3.9.9）+ PostgreSQL 17 + Redis + MyBatis-Plus + Flyway；测试 JUnit5 + Mockito + H2（`BaseDbUnitTest`）/ 独立 Redis 夹具；治理工具链 `scripts/ops/worktree-orchestrate.mjs`、`scripts/gov/close-task.mjs`、`scripts/gov/verify-docs.mjs`、`scripts/ops/run-local-gates.mjs`；评审 codex（gpt-6-astra/xhigh）。

- 测试：`services/zhongshu-core/zszj-framework/zszj-spring-boot-starter-web/src/test/java/cn/zszj/framework/web/config/CorsConfigTest.java`（新建）

**现状证据：**
- `ZszjWebAutoConfiguration.corsFilterBean()`（106-119）：`setAllowCredentials(true)` + `addAllowedOriginPattern("*")` + `addAllowedHeader("*")` + `addAllowedMethod("*")`，对 `/**` 全通配。
- `ZszjWebSecurityConfigurerAdapter.filterChain()`（110-122）：`.cors(withDefaults())` + `.csrf(disable)` + `sessionManagement(STATELESS)` + `.headers(frameOptions disable)`。
- `WebProperties` 现仅有 `appApi/adminApi/adminUi/requestBody`，**无 CORS 配置项**。

### 2.1 设计决策（执行前须与用户确认的默认取值）

- **允许来源**：改为**显式白名单**（从 yaml 读 `zszj.web.cors.allowed-origin-patterns`），默认仅放行本地开发源（如 `http://localhost:*`、`http://127.0.0.1:*`）；生产源在 `application-prod.yaml` 按实际域名配置。**不再用 `*` 全通配 + credentials=true 的危险组合**（该组合被浏览器拒绝且是安全隐患）。
- **allowCredentials**：保持 `true`（两端请求层依赖 Cookie/凭据语义），但因来源已收窄为精确白名单，符合 CORS 规范（精确源 + credentials 合法）。
- **允许方法/头**：从 yaml 读，默认方法 `GET,POST,PUT,DELETE,OPTIONS,PATCH,HEAD`，头 `Authorization,Content-Type,X-Requested-With,tenant-id`（含租户头），暴露头 `trace-id`（与 ZS-SEC-006 联动预留）。
- **CSRF**：因 `STATELESS` + Token（非 Cookie 会话）模型，保持 `disable`，但在配置类注释明确依据；若未来引入 Cookie 会话须重开（本 Wave 不引入）。
- **frameOptions**：从「机械全关」改为可配置——默认 `SAMEORIGIN`（防点击劫持），如需嵌入由 yaml 显式放开；不无条件 disable。

- 修改：`.../idempotent/core/aop/IdempotentAspect.java:48-54`（锁失败时比对摘要：同摘要=重复、异摘要=冲突）
- 测试：`.../idempotent/core/keyresolver/impl/DefaultIdempotentKeyResolverTest.java`（新建，纯单测）
- 测试：`.../idempotent/core/aop/IdempotentAspectTest.java`（已存在 200 行，扩展同键异参冲突 + 主体隔离用例）

**现状证据：**
- `DefaultIdempotentKeyResolver.resolver()`（18-23）：`MD5(methodName + argsStr)`——**无租户/主体**，卡片 line 402 明确"没有自动加入服务端租户/主体"。
- `IdempotentRedisDAO.setIfAbsent`（27-30）：`setIfAbsent(redisKey, "", timeout)`——**存空值**，锁失败时无法区分"同键同参重复"与"同键异参冲突"。
- `IdempotentAspect.aroundPointCut`（48-54）：`setIfAbsent` 失败即抛 `REPEATED_REQUESTS`，不比对请求内容。

### 4.1 设计决策

- **主体隔离**：`DefaultIdempotentKeyResolver` 返回 `MD5(methodName + ":" + tenantId + ":" + userId + ":" + userType + ":" + argsStr)`——不同主体/租户不误用他人幂等结果（满足验收"不同主体不误用他人结果"、退出条件"主体隔离有合同用例"）。复用 `UserRateLimiterKeyResolver` 同款上下文路径（`WebFrameworkUtils.getLoginUserId/getLoginUserType` + `TenantContextHolder.getTenantId`）。
- **同键异参冲突**：`IdempotentRedisDAO.setIfAbsent` 存**请求摘要**（argsStr 的 MD5）为 value；`IdempotentAspect` 锁失败时读回已存摘要比对——**相同**=真重复请求（抛 `REPEATED_REQUESTS`，窗口防重）；**不同**=同键异参冲突（抛 `REPEATED_REQUESTS` 但用冲突专属 message，明确拒绝而非静默复用）。满足退出条件"同键异参冲突…有合同用例"。
- **不承诺持久化幂等**：窗口锁是**短时防重**（Redis TTL 窗口），进程重启/超时/缓存故障后不保证返回原业务结果——这是 ZS-SEC-011.B（B05，持久化幂等 + HTTP 重试联验）的范围。本批合同测试**显式声明**该边界（退出条件"不以窗口锁承诺持久化结果"）。
- **不新增框架级错误码**：冲突复用 `GlobalErrorCodeConstants.REPEATED_REQUESTS` + 注解 `message()`/冲突 message，避免改 `framework/common`（共享、宽影响）。

package cn.zszj.module.infra.service.config;

import cn.zszj.module.infra.dal.dataobject.config.ConfigDO;
import org.springframework.stereotype.Component;
import java.util.List;
import java.util.regex.Pattern;

/** ZS-CFG-001.B：参数敏感级分类器，复用 CFG-001.A 三档分类（秘密/敏感/普通）。 */
@Component
public class ConfigSensitiveClassifier {

    public enum SensitiveLevel { SECRET, SENSITIVE, NORMAL }

    /** 秘密键模式（移植 scripts/cfg/verify-config-secrets.mjs 键集，小写归一 contains 匹配）。 */
    private static final List<String> SECRET_KEY_TOKENS = List.of(
            "password", "passwd", "secret", "token", "apikey", "api_key",
            "privatekey", "private_key", "credential", "accesskey", "access_key");

    public SensitiveLevel classify(ConfigDO config) {
        String key = config.getConfigKey() == null ? "" : config.getConfigKey().toLowerCase().replace("-", "").replace("_", "");
        boolean secretKey = SECRET_KEY_TOKENS.stream().anyMatch(t -> key.contains(t.replace("_", "")));
        if (secretKey) {
            return SensitiveLevel.SECRET;
        }
        if (Boolean.FALSE.equals(config.getVisible())) {
            return SensitiveLevel.SENSITIVE;
        }
        return SensitiveLevel.NORMAL;
    }

    /** 秘密/敏感项的 value 掩码；普通项原样。 */
    public String maskValue(ConfigDO config) {
        return classify(config) == SensitiveLevel.NORMAL ? config.getValue() : "******";
    }
}

- `AdminUserMapper.selectListByDeptIds`（53-55）可查部门下用户；`DeptMapper` 无按 leader 计数方法。

### 7.1 设计决策

- **部门删除引用保护**：`deleteDept`/`deleteDeptList` 在子部门校验后，增加"部门下有成员"校验——用 `AdminUserMapper`（mapper 级注入避免与 `AdminUserService` 的服务层循环依赖）查 `selectListByDeptIds` 是否非空（或新增 `selectCountByDeptId`），有成员则抛新码 `DEPT_EXITS_USERS`（1_002_004_005）。满足验收"挂有成员/引用的删除按批准规则处理"（本批规则=阻止，受控迁移待 D-09 任职模型）。
- **用户删除引用保护（负责人）**：`deleteUser`/`deleteUserList` 增加"用户是部门负责人"校验——`DeptMapper.selectCountByLeaderUserId(userId)>0` 则抛 `USER_IS_DEPT_LEADER`（1_002_003_007），要求先变更负责人再删，**不自动级联抹除负责人历史**（卡片"不自动级联抹除历史"）。满足验收"停用负责人不能无提示继续承担新任务"的删除侧对应。
- **责任历史合同边界**：完整任职生命周期/历史归属迁移是 ZS-IAM-004（B07，前置 D-09 任职模型）；本批只做**技术层引用保护**（部门在用、负责人有效性、批量与单条一致校验），业务职责归属待 D-09。§16.1 line 1003 明确"ZS-IAM-003 的技术生命周期在 B03 验，任职扩展归 ZS-IAM-002/004"。
- **批量与单条一致**：`deleteDeptList`/`deleteUserList` 复用与单条相同的引用校验（逐项），满足验收"批量与单条具有一致校验和审计"。
- **并发调层不成环**：卡片"并发层级更新不成环"——`updateDept` 已有 `validateParentDept` 环路检查（第 118-129 行 `DEPT_PARENT_IS_CHILD`），本批复核该检查在并发下的充分性，不足则登记（完整并发合同可归 ZS-DB-019.B/PERM）。

## 11. 执行方式选择（Execution Handoff）

本计划已就绪。两种执行方式：

**方式 A — Subagent 驱动（推荐）：** 每个 worktree 派一个**全新子代理**独立执行 §1.2 的 9 步周期（5 树可真并行推进），任务间由主会话做**两阶段评审**（先审 RED/GREEN 与门禁证据，再审 codex 结论）。合并与文档串行同步（§8）由主会话在主树统一执行，严守「代码并行、文档串行」铁律。契合本 Wave 的 5-worktree 物理隔离结构，隔离性最好、上下文最干净。

**方式 B — 会话内联执行：** 在当前会话按 §8.1 推荐顺序**逐 worktree 分批执行**，每完成一个任务在检查点（§10.1/§10.2）暂停供你复核后再继续。上下文连续、便于你逐步介入，但并行度低于方式 A。

**请选择 A 或 B。** 无论哪种，首个动作都是 §1.1 环境前置校验（确认主树在 `main`、工作区干净、`tools/` 已自引导），随后按 §8.1 次序 1 对 WT-1（ZS-SEC-004）执行 `worktree-orchestrate.mjs plan`→`create`。

> **执行前须与用户确认的设计默认值**：§2.1（SEC-004 CORS 白名单默认源、frameOptions=SAMEORIGIN、CSRF 保持 disable 的依据）、§3.1（SEC-010 fail-open 默认策略、测试用小阈值而非生产值）、§6.1（LOGIN-001 兼容开关默认 false、报表/WebSocket 审计若判定活跃的迁移口径）。这些默认值已在各任务「设计决策」写明推荐取值，执行时若与你的环境预期不符，请在开工前指出以便调整。
