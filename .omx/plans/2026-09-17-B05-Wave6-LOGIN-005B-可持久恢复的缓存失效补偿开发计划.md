## 2. 设计决策（收口论证）

1. **补偿事件语义 = "重放撤销"而非"记录失败"**：Sink `deliver` 的动作 = **重新调用 `revokeWithTombstone(token, expiresTime)`**（幂等：markRevoked + delete 本就幂等），而非"记日志"或"回写业务事实"（`OutboxEventSink` 合同第 2 条明禁）。这直接满足退出条件"补偿可重放"（多次 dispatchOnce 结果一致）+ "不复活凭据"（Sink 结构上无写缓存路径，只有 markRevoked + delete）。

2. **payload 秘密扩散防护 = 存 DB 主键 id 而非 token 明文**：token 是访问凭据（`OAuth2AccessTokenDO.accessToken` / `OAuth2RefreshTokenDO.refreshToken` 均 varchar 明文），若入 `outbox_event.payload` 即扩大秘密扩散面（与 ZS-SEC-007 日志脱敏原则、ZS-CFG-001 秘密门禁冲突）。**决策**：payload 存 `{tokenId: long, tokenType: "ACCESS"|"REFRESH", expiresTime: "ISO-8601", failedStep: "MARK_REVOKED"|"DELETE"|"BOTH"}`；Sink `deliver` 内按 `(tokenType, tokenId)` 从 DB 反查原 token 串（DB 是权威源，本就存明文），行已删（自然清理/物理删除）→ **skip 不重放**（`OutboxRecoveryAction.SKIP` 语义或 deliver 内静默返回，见决策 6）。**收益**：Outbox 表零秘密扩散；重放仍拿到原 token 作 Redis key。

3. **event_type / biz_type 命名合同**（自由字符串，无枚举表）：
   - `event_type = "zszj.system.oauth2.token.revocation-compensation"`（反向域名 + 域 + 对象 + 动作，循 JOB-002 outbox 命名惯例）
   - `biz_type = "oauth2_access_token"` 或 `"oauth2_refresh_token"`（按 tokenType 分型，便于 JOB-004 恢复台账按业务类型筛选）
   - `biz_id = tokenId.toString()`（DB 主键字符串化，`outbox_event.biz_id` 是 text）
   - 常量登记在 `zszj-module-system/framework/outbox/SystemOutboxEventTypes.java`（新增，package-private 常量类，与 `AuditEventTypes` 分层——审计事件 vs 领域补偿事件语义分离）

4. **写路径注入点 = 撤销主逻辑内「预写 outbox 事件」（修订版，遵循 JOB-002 SPI 合同）**：
   - **修订背景**：`ReliableEventPort` SPI 合同明禁业务模块直读 `outbox_event` 表、且 `append` 必须在业务事务内（MANDATORY，无事务即拒绝，不代开事务）。原方案（catch 分支 REQUIRES_NEW 短事务 + 自建 `JdbcSystemOutboxEventPublisher`）双重违反合同，已修订为「预写策略」。
   - **注入点**：3 处写路径撤销主逻辑内**预写 outbox 事件**（在事务体内、`invalidateCacheAfterCommit` 注册前）：
     - `refreshAccessToken`（L156~L173 淘汰旧代际）：每个被淘汰的 `OAuth2AccessTokenDO` 预写一条事件（tokenType=ACCESS，tokenId=evicted.getId()）
     - `removeAccessToken`（L295~L320 单会话退出）：每个 aliveToken 预写一条 ACCESS 事件 + refreshToken 预写一条 REFRESH 事件
     - `removeAccessTokenByUser`（L470~L496 用户级撤销）：同上，遍历所有 aliveTokens 逐个预写
   - **读路径不预写**（`checkAccessToken` 自愈 L245~L252）：§1 边界第 1 条维持不变（读路径无事务、每请求执行，扩爆炸半径）
   - **`revokeWithTombstone` 签名不改**（`.A` 语义零改写）：预写 outbox 事件与 `revokeWithTombstone` 调用**并列**（撤销主逻辑内先预写事件、再注册 afterCompletion 执行 `revokeWithTombstone`），失效失败仍走 `.A` 原 WARN 路径；补偿由 dispatcher 后续重放承担
   - **payload schema**：`{tokenId: long, tokenType: "ACCESS"|"REFRESH", expiresTime: "ISO-8601"}`（无 failedStep——预写时尚不知道会不会失败；Sink 反查 DB 判定重放策略）
   - **调用方式**：`reliableEventPort.append(OutboxEventMessage.builder().eventType(...).bizType(...).bizId(tokenId.toString()).payload(Map.of(...)).actorType(SYSTEM).build())`——**直接注入 infra `ReliableEventPort`**（`ObjectProvider<ReliableEventPort>` 懒解析，system 单独运行测试时降级为 `.A` 原语义）

5. **事务原子性 = 复用 JOB-002 `ReliableEventPort.append`（MANDATORY 传播，与业务事务同源）**：
   - **零 infra 侧新增**：直接注入既有 `ReliableEventPort` Bean（`JdbcReliableEventPort` 已由 infra 装配）
   - `PROPAGATION_MANDATORY`：无事务 → `IllegalTransactionStateException` fail-closed；调用点均在 `OAuth2TokenServiceImpl` 的 `@Transactional` 方法内，天然满足
   - **提交原子性**：业务事务提交 → outbox 事件同提交；业务事务回滚 → outbox 事件同回滚（无假事件、无「业务回滚但事件留存」窗口）
   - **`.A` 关键交互点**：预写发生在事务体内（非 afterCompletion），与 `.A` 的 `invalidateCacheAfterCommit` 注册顺序：先 `append(event)` → 后 `invalidateCacheAfterCommit(desc, evictions)`（顺序无强依赖，均在事务体内）
   - **业务提交后 afterCompletion 内 Redis 失效**：
     - **失效成功**：outbox 事件保持 PENDING；dispatcher 后续派发 → Sink 反查 DB `deleted=1` + Redis 已无 key → 幂等重放（`markRevoked` SET NX 无副作用 + `delete` 已无 key 无副作用）→ dispatcher 标 SUCCESS
     - **失效失败**：`.A` 原 WARN 日志照旧；outbox 事件保持 PENDING；dispatcher 后续派发 → Sink 反查 DB `deleted=1` + Redis 仍有 key → 重放 `markRevoked + delete` 生效 → dispatcher 标 SUCCESS（**补偿可重放主证据**）
   - **业务回滚**：outbox 事件同回滚（无事件写入）；afterCompletion 内 `.A` 语义仍执行失效（回滚补偿，宁可抖动不留撤销态不一致）；失效失败仅 WARN，无补偿必要（DB 中 token 仍活跃，缓存 miss 回源即修复，无安全缺口）

6. **Sink 实现（`OAuth2TokenRevocationCompensationSink`）**：
   - `supports(eventType)` → `SystemOutboxEventTypes.TOKEN_REVOCATION_COMPENSATION.equals(eventType)`
   - `deliver(record)`：
     1. `JsonUtils.parseObject(record.getPayload(), TokenRevocationCompensationPayload.class)` → 反序列化 `{tokenId, tokenType, expiresTime}`
     2. **过期识别**：`expiresTime.isBefore(LocalDateTime.now())` → **静默返回**（凭据已自然过期，Redis key TTL 到期自清理，无需墓碑；不视为失败、不写 recovery_log）
     3. **DB 反查原 token + 撤销状态**：按 `tokenType` 分派 `oauth2AccessTokenMapper.selectByIdIncludeDeleted(tokenId)` / `oauth2RefreshTokenMapper.selectByIdIncludeDeleted(tokenId)`（新增 `@Select` 专用语句绕逻辑删除，循 `.A` `selectAuthorityCountByAccessToken` 惯例，`@Options(flushCache=TRUE)` 保权威；返回 `TokenRowSnapshot{token, deleted, expiresTime}`）
     4. **业务回滚保护（关键新增）**：`deleted == 0` 且 `expiresTime > now` → **静默返回**（token 仍活跃，说明业务事务已回滚或撤销未生效，重放会误撤销有效凭据 —— 结构上不可能复活凭据的对偶保证：**结构上不可能误撤销有效凭据**）
     5. **行已物理删除**（DB 中彻底不存在，如 DBA 手工清理）→ **静默返回**（Sink 合同"只做投递动作"，物理删除后无补偿目标，视为已完成）
     6. **重放撤销**（`deleted == 1` 或 `expiresTime <= now` 但 DB 仍有行）：调用 `oauth2AccessTokenRedisDAO.markRevoked(token, ttlMillis)` + `.delete(token)`（**幂等**：markRevoked 是 SET NX + EXPIRE，重复写结果一致；delete 重复调用无副作用；Redis 已失效则为空操作）；两项各自 try/catch，任一失败 → `throw ex`（触发 dispatcher 计数 +1、退避重试、达上限 DEAD）
     7. **不复活凭据保证**：Sink 全代码路径**无任何 `redisTemplate.opsForValue().set(accessTokenKey, ...)`**（结构上不可能写回缓存）；code review + 静态测试断言（`SinkNeverWritesAccessTokenCacheTest` 反射扫描 Sink 类的所有方法调用图，断言无 `set` / `put` / `write` 类调用指向 access-token key 空间）
   - Bean 注册：`zszj-module-system/framework/outbox/config/ZszjSystemOutboxAutoConfiguration.java`（新增，`@Configuration` + `@Bean OAuth2TokenRevocationCompensationSink`），循 system 模块既有 `ZszjXxxAutoConfiguration` 惯例，通过 `spring.factories` / `AutoConfiguration.imports` 装配

7. **`OAuth2TokenServiceImpl` 依赖注入**：
   - `@Resource private ObjectProvider<ReliableEventPort> reliableEventPortProvider;`（**直接复用 infra 侧 JOB-002 既有 SPI，零 infra 侧新增**）
   - 懒解析：`reliableEventPortProvider.getIfAvailable()` 返回 null（system 单独运行测试 profile 未装配 infra）→ 降级为 `.A` 原语义（仅 WARN 日志，无 outbox 事件写入）；这与 `.A` `AuthorityUnitTest` 裸 `new OAuth2TokenServiceImpl()` + `ReflectionTestUtils.setField` 测试模式兼容
   - **无 `SystemOutboxEventPublisher` 中间层**（原决策 8 撤销）：调用点直接构造 `OutboxEventMessage` 并调 `append`，薄封装无价值

8. **分层与依赖方向**（修订版，防环）：
   - `SystemOutboxEventTypes`（`zszj-module-system/framework/outbox/`）：常量类，登记 event_type / biz_type 字符串

## 5. 登记边界（红线，收口如实声明）

1. **读路径自愈失败无 Outbox 补偿**：`checkAccessToken` 内 `revokeWithTombstone` 失败仍仅 WARN，依赖下次访问再自愈。安全底线由 DB 权威 count 核验保证（幽灵缓存 = 拒绝服务的可用性抖动，非安全缺口）；若某 token 长期不再走读路径，幽灵缓存活到自然 TTL 到期（access-token 默认 30 分钟、refresh-token 默认 30 天）。**不承诺"零幽灵缓存窗口"**。
2. **PERM-004.A 权限缓存驱逐失败的可靠补偿不在本卡**：`RetryCacheErrorHandler` 重试耗尽路径的失败键清单持久化，涉及 permission 域事件合同与 `.B`（B08 组织权限）语义强绑定，**登记为独立小卡**（未来 ZS-PERM-004.C 或 ZS-LOGIN-005.C，待 B08 拍板）。本卡聚焦 OAuth2 token 撤销单域。
3. **每撤销操作 IO +1（outbox INSERT）**：预写策略下每次撤销都写 outbox 事件（无论 Redis 失效成败），IO 放大 1 倍；正常路径事件由 dispatcher 派发后 Sink 幂等空操作 → SUCCESS。**不承诺 outbox 表零膨胀**，长期清理策略归 JOB-004 恢复台账既有能力（不在本卡）。撤销操作频率远低于登录/查询，IO 影响可接受。
4. **`dispatchOnce` 生产调度接线归 D-07**：本卡以测试内 + PG 脚本内**手动触发** dispatcher 证明 Sink 语义正确；生产环境定时调度接线（Quartz JobHandler 或 `@Scheduled`）不在本卡范围（JOB-002 登记边界维持不变）。
5. **Redis Cluster 集群语义等价性归 B11**：本卡以单机内嵌 Redis（H2 测试）+ 一次性 Docker Redis（PG 脚本）证明补偿合同；集群级 markRevoked/delete 的跨 slot 行为、集群故障转移期间的事件重放语义归环境验收批次（ZS-OPS-002 / ZS-SEC-012.B）。
6. **主卡 ZS-LOGIN-005 状态迁移**：`.A`（B03）✅ + `.B`（B05）本轮交付 → 主卡从"开发中"转"待验收"（`.B` 交付≠主卡已验收；批次真实环境放行归轨 C 验收批次）。
7. **本卡零迁移交付**：复用 JOB-002 已建 `outbox_event` 表；若测试或 PG 脚本发现需要索引（如 `event_type + status` 组合索引以支撑 Sink 侧查询性能），另立小卡（不在本卡扩爆炸半径）。
8. **`.A` 已交付代码零改写**：本卡仅在 `revokeWithTombstone` catch 分支**新增** Outbox 事件写入调用，不改 `.A` 三层闭环任一语义（DB 权威 count / afterCompletion 单次执行 / WARN 结构化日志）；`.A` 既有 8+1+5 用例（CacheConsistencyTest / GateOnTest / AuthorityUnitTest）**全绿不破**为合并前置门禁。
