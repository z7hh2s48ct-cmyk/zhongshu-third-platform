## 2. 设计决策（收口论证）

### D1 记录点唯一化 = RetryEvictCache（afterCommit 路径唯一证据点）
- afterCommit 回调最终落在 `RetryEvictCache.evict/clear`（装饰链事实），`CacheErrorHandler` 不覆盖该路径（PERM-004.A 注释已证）；非事务路径下 handler 的重试也**经由装饰链**（handler 调 `cache.evict` → RetryEvictCache）→ 记录点仅需 RetryEvictCache 一处。
- `RetryCacheErrorHandler` **不接 recorder**（防同一失败被双层重试重复记录），仅更新 2 处过时文本。
- 记录时机：`boundedRetry` 重试耗尽（`attempt >= MAX_RETRIES`）分支，与既有 ERROR 日志同处；每次最终失败记 1 条。

### D2 SPI 接口（框架层定义，依赖反转）
```java
// cn.zszj.framework.redis.core.CacheEvictionFailureRecorder
public interface CacheEvictionFailureRecorder {
    void record(String cacheName, @Nullable String key, CacheEvictionOperation operation, RuntimeException cause);
}
// cn.zszj.framework.redis.core.CacheEvictionOperation — enum { EVICT, CLEAR }
```
- 默认无实现（`ObjectProvider` 空）→ 保留现状行为（仅 ERROR 日志），**非白名单/未装配时零变化**。
- 框架层调用 recorder 必须 try/catch 包裹（记录失败仅追加 ERROR 日志，不传播、不影响驱逐返回值）。
- 实现方契约：幂等容忍（框架可能对同一键重复调用）；kv 中 `key=null` 表示 CLEAR。

### D3 重放抑制（防「记录→重放→再记录」自我循环）= CacheEvictionReplayContext
```java
// cn.zszj.framework.redis.core.CacheEvictionReplayContext
public final class CacheEvictionReplayContext {
    public static boolean isInReplay();
    public static void runInReplayScope(Runnable action); // finally 还原
}
```
- RetryEvictCache 记录前检查 `isInReplay()` → 重放中失败**不再产生新事件**（仍执行有界重试），交由 dispatcher 退避重试、超限 DEAD + JOB-004 人工台账（与 LOGIN-005.B 边界 4 同范式）。
- Sink 重放动作以 `runInReplayScope` 包裹。

### D4 版本机制（防旧值写回）= CacheVersionGuard + RetryEvictCache 增强
- **版本存储**：Redis 独立前缀键 `{keyPrefix}__cachever__:{cacheName}`（keyPrefix 归一化规则与 `redisCacheConfiguration.computePrefixWith` 同，当前 key-prefix 为空 → 实际键 `__cachever__:role`）。**不放在 `{cacheName}:` 前缀下**——RedisCache.clear() 的 SCAN 模式（`{cacheName}:*`）不得误删版本键（测试 29 钉住）。
- **命令**：`RedisTemplate.execute(RedisCallback)` 走原始字节 `INCR` / `GET`（不经 value 反序列化，规避 JSON 歧义）；GET null → 0。
- **evict/clear 增强**（受管缓存）：**先 bump（INCR）→ 后 delegate 操作**，两者作为一个 operation **整体**有界重试（bump 多次幂等无害）；整体失败 → 记录补偿（`operation=EVICT/CLEAR`）。语义：bump 成功即宣告「本 key 空间代际已推进」，在途写回将被拦截；delegate 失败由清单补偿重放。
- **get miss 快照**（受管缓存）：`delegate.get` 返回 null → 读当前版本存**本线程快照**（`ThreadLocal<Map<Object,Object>>`，per-instance；读失败 → 存入不可校验哨兵）；命中 → 清除该键快照。
- **put 校验**（受管缓存）：有快照 → 读当前版本对比：**相等 → 写；不等 → 丢弃写回（晚到回填拦截）+ DEBUG 日志**；哨兵 → 丢弃（fail-safe 不缓存，回源自愈）；无快照 → 直接写（@CachePut 等非常规路径，登记）。
- **跨节点语义**：版本存 Redis 共享 → 任意节点驱逐 bump 后，其他节点在途加载的写回均被拦截（本地版不具备，明确选用共享版）。
- **理论残余窗口**：verify（GET 版本）与 `delegate.put` 之间的亚毫秒间隙（两相邻 Redis 调用之间，无 DB 操作）；彻底原子化需 Lua 侵入（不做，§5-1 登记）。相对修复前窗口（跨 DB 查询毫秒级、可被屏障拉长至秒级）收窄 3~4 个数量级。
- `get(key, type)` 与 `get(key)` 同逻辑；`get(key, Callable)` / `putIfAbsent` 透传（§5-2 登记）。

### D5 受管范围 = 白名单配置（框架层通用，应用层显式声明）
- `ZszjCacheProperties` 新增 `List<String> consistencyGuardedCacheNames = new ArrayList<>()`（前缀 `zszj.cache.consistency-guarded-cache-names`；**默认空 = 框架行为与现状完全一致**，零回归面）。
- `application.yaml` 显式配置权限 4 缓存：
  ```yaml
  zszj:
    cache:
      consistency-guarded-cache-names:
        - role
        - user_role_ids
        - menu_role_ids
        - permission_menu_ids
  ```
- 框架层不硬编码业务缓存名（`role` 等为 system 模块语义）；白名单同时控制「补偿记录」与「版本校验」两项能力；非白名单缓存零开销零行为变化。

### D6 应用层实现（system 模块，复用 outbox，零 infra 侧新增）
- **事件类型**（`SystemOutboxEventTypes` 追加）：
  - `CACHE_EVICTION_COMPENSATION = "zszj.system.cache.eviction-compensation"`
  - `BIZ_TYPE_CACHE_EVICTION = "cache_eviction"`；`biz_id = cacheName + ":" + (key == null ? "__clear__" : key)`。
- **payload POJO**（`CacheEvictionCompensationPayload`，@Value @Builder）：`{cacheName, key(String, 可空=clear), operation("EVICT"|"CLEAR"), failedAt(ISO-8601)}`——**零秘密扩散**（仅缓存名/键/操作，缓存键为 ID 数字；异常对象不入载荷，只进日志）。
- **Recorder 实现**（`OutboxCacheEvictionFailureRecorder`，@Component）：
  1. **进程内去重**：`ConcurrentHashMap<cacheName+":"+key+":"+operation, epochMillis>`，5 秒窗口同键重复记录跳过（框架可能双层重试致重复调用）；
  2. **自开事务**：`TransactionTemplate(transactionManager)`（驱逐失败点无事务，REQUIRED 即新开）→ 事务内 `port.append(message)`（满足 MANDATORY；单库拓扑与端口同 TM 同源）；
  3. **租户**：`TenantContextHolder` 缺失 → 记 ERROR 降级返回（不伪造归属，循 JdbcReliableEventPort 合同）；
  4. `ObjectProvider<ReliableEventPort>` 懒解析（infra 未装配场景降级，循 LOGIN-005.B 先例）；`actorType=SYSTEM`；`traceId=TracerUtils.getTraceId()`；
  5. 全流程 try/catch：记录失败仅 ERROR（补偿证据丢失的降级路径）。
- **Sink**（`CacheEvictionCompensationSink`，@Component，实现 `cn.zszj.module.infra.framework.outbox.OutboxEventSink`）：
  1. `supports(eventType)` 直判；
  2. `deliver`：解析 payload（失败 → **抛异常**，进 dispatcher 退避/DEAD 人工可见，不静默丢）→ `runInReplayScope` 内执行：`cacheManager.getCache(cacheName)`（null → 静默返回：无目标视为完成）→ `EVICT: cache.evict(key)` / `CLEAR: cache.clear()` → 失败抛异常（触发 dispatcher 计数 +1、退避、超限 DEAD）；
  3. **幂等**：evict/clear 天然幂等（重复重放=再驱逐一，多清无害）；重放驱逐可能清除重放时点后新写入条目（毫秒级误清→回源重建自愈，性能抖动非一致性缺口，§5-3 登记）。
- **装配**：两个类以 @Component 注册（循 `OAuth2TokenRevocationCompensationSink` 先例，无需新增 config 类）。

### D7 装配链接线（ZszjCacheAutoConfiguration → TimeoutRedisCacheManager → RetryEvictCache）

## 5. 登记边界（红线，收口如实声明）

1. **版本机制理论残余窗口**：verify（GET 版本）与 `delegate.put` 之间的亚毫秒间隙内并发驱逐仍可致旧值一次存活（彻底原子化需 Lua 侵入 RedisCache 写入语义，不做）；相对修复前窗口（跨 DB 查询毫秒级、可被屏障拉长至秒级）收窄 3~4 个数量级。**不承诺零窗口**。
2. **`get(key, Callable)`（sync=true）/ `putIfAbsent` 路径不做版本校验**：当前仓库零使用（静态搜索证据齐全）；若未来引入需扩展本机制（登记防漂移）。
3. **重放驱逐的时序语义**：重放可能清除重放时点之后新写入的条目（毫秒级误清）→ 回源重建自愈，性能抖动非一致性缺口（对齐 PERM-004.A「权限链路宁可多清不留旧」）。
4. **补偿链对 Redis 持续不可用的兜底依赖 JOB-004 DEAD 台账人工恢复路径**（循 LOGIN-005.B 边界 4）。
5. **多节点/集群 Redis 语义联验归环境批次**：本卡以 H2+内嵌 Redis 单机语义等价论证；版本键存 Redis 共享的设计对多节点天然成立（任意节点 bump 全局可见），集群级行为归环境验收。
6. **真实 PG 层**：零迁移零表结构变更；`outbox_event` 的 PG 语义由 JOB-002/JOB-004 既有套件持续保障；本卡不新增 PG 脚本（新增链路以 H2+内嵌 Redis 端到端为权威）。
7. **租户上下文缺失时记录降级**：不阻断、不伪造归属（循 JdbcReliableEventPort 合同）；该场景补偿证据丢失，仅 ERROR 留痕。
8. **主卡 ZS-PERM-004 维持「开发中」**：理由 ①（.C 未交付）解除，理由 ②（B08 真实环境放行：撤权后旧 Token/旧菜单不继续执行受限动作、多节点缓存广播、审计端到端）仍挂账；**本卡不改变任何主任务验收状态，第 2 节统计不变（0/20/2/0/3/66，合计 91）**。
9. **`OAuth2TokenServiceImpl` 同类过时文本**（L828/L840 附近「归 ZS-LOGIN-005.B」）属登录域留痕，不在本卡更新。
