# B03 Wave 4 开发计划：ZS-PERM-004.A（角色/菜单缓存和停用撤权的技术一致性）

> 地面真相：前置 LOGIN-005.A✅（10552888）、PERM-001.A✅ 均满足；§16.1 本批交付「多节点/回滚/回填测试；旧 Token 不保留撤销权限」。

## 勘查结论（真实现状）

缓存 = Redis Spring Cache（`TenantRedisCacheManager`：key 拼租户后缀；`ignoreCaches` 列表内的缓存名共享单键空间）。

1. **双键空间错位**：`user_role_ids`、`permission_menu_ids` 在 ignore-caches，但 `role`、`menu_role_ids` 不在——同为全局主键 id 键。租户上下文写入只驱逐带后缀键，ignore 上下文读取填充裸键 → 裸键可长期陈旧。
2. **驱逐早于提交（并发回填）**：`@CacheEvict` 在方法返回后、事务提交前执行 → 并发读者在「已驱逐、未提交」窗口回读库中旧值重新入缓存 → 提交后陈旧权限存活（卡片所指「缓存驱逐、事务提交、其他节点读取的组合」）。
3. **事务回滚误清**：回滚路径同样已驱逐 → 「清缓存当万能修复」损失一致性证据。
4. **@DSTransactional 隐患**：`assignRoleMenu`/`assignUserRole` 用动态数据源本地事务，Spring `TransactionSynchronization` 不激活——直接套「提交后驱逐」会退化为立即驱逐；system 模块单库，改用 `@Transactional`。
5. MenuServiceImpl 的 update/delete 已用 allEntries（新老 permission 一并清），无新老公权利键残留问题。

## 交付（B03.A 技术一致性）

- **F1** 新增 `CacheEvictAfterCommitHelper`（system 模块）：驱逐步骤 `List<Runnable>` 在事务结束后（afterCompletion 全状态）单次执行、逐项容错并记录证据；无事务上下文立即执行（等价 @CacheEvict 原语义）。复用 LOGIN-005.A 已验证的事务同步模式。
- **F2** 12 处驱逐点改造：RoleServiceImpl（updateRole/updateRoleDataScope/deleteRole/updateRoleStatus）、PermissionServiceImpl（assignRoleMenu/processRoleDeleted/processMenuDeleted/assignUserRole/processUserDeleted）、MenuServiceImpl（createMenu/updateMenu/deleteMenu/deleteMenuList）——移除 @CacheEvict，改为提交后驱逐；assignRoleMenu/assignUserRole 由 @DSTransactional 改 @Transactional。
- **F3** 配置：`role`、`menu_role_ids` 加入 `zszj.tenant.ignore-caches`（id 为全局主键，消除双键空间错位）。
- **TDD**：并发回填 RED（事务内读者回填旧值、提交后必须取到新值）、回滚 RED（回滚不得误清缓存）、停用角色后 hasAnyPermissions 立即失效（旧 Token 不保留撤销权限）、撤销角色授权后失效等。

## 边界（不做）

- 撤权审计字段（操作者/目标/变更）→ ZS-PERM-004.B（B08，前置 IAM-004）；
- 真实多节点联验 → 归环境批次（本批以事务同步语义 + Redis 真实缓存单测等价证明）。
