## 1. 目标与范围

修复 ZS-DB-009 已实证的缺陷：`system_users` 的 username/mobile/email 仅普通索引、应用层「先查重后写入」（`validateXxxUnique` + 租户内 `selectByUsername`）在并发与跨租户下均无法拦截，产生重复账号。本卡按 D-09 批准矩阵以**数据库层唯一约束为最终防线**收口，应用层查重保留为友好提示。

**批准的唯一性矩阵（docs/07 §4）：**
| 项 | 决策 | 落地 |
|---|---|---|
| M1 用户名作用域 | 全平台唯一（跨租户不可重名） | 全局唯一索引（不含 tenant_id） |
| M2 规范化 | 统一 trim + 小写化存储 | 迁移清洗存量 + 应用层写入前规范化 + `lower()` 表达式索引兜底 |
| M3 手机/邮箱 | 全局唯一，NULL/空允许多个 | 部分唯一索引排除 NULL 与空串 |
| M4 删除后重用 | 逻辑删除后允许重建 | 部分唯一索引 `WHERE deleted = 0`（复用 ZS-CFG-002.A 范式） |

**范围内：** system_users 的 username/mobile/email 唯一约束、存量规范化、历史冲突报告、DB 冲突→稳定错误码映射、并发兜底验证、登录名规范化兼容。
**范围外（明确边界）：** 不创建 Account/Membership/Organization 新表（归 ZS-IAM-001，B07 后续）；不做组织级/字段级授权（归 ZS-PERM-002.B/003）；不擅自删除任何历史重复数据。

## 2. 关键设计决策（决策完整，实施者无需再抉择）

### D1 迁移脚本 `V20260920.001__system_users_account_unique.sql`
按序三段，任一段失败即整体回滚（Flyway 事务内）：

1. **历史冲突报告（fail-loudly，禁止擅自删重）**：加约束前先探测存量冲突，若有则 `RAISE EXCEPTION` 打印冲突键与行 id，令升级失败交人工按批准方案处置，绝不自动删重/合并。
   - username：`lower(btrim(username))` 分组 `WHERE deleted = 0 HAVING count(*) > 1`
   - mobile：`mobile` 分组 `WHERE deleted = 0 AND mobile IS NOT NULL AND mobile <> '' HAVING count(*) > 1`
   - email：同 mobile 口径
2. **存量规范化（M2）**：`UPDATE system_users SET username = lower(btrim(username)) WHERE username IS DISTINCT FROM lower(btrim(username))`。仅规范化 username（登录名），email/mobile 不改大小写（超批准范围）。
3. **建部分唯一索引（M1/M3/M4）**：
   ```sql
   CREATE UNIQUE INDEX uk_system_users_username ON system_users (lower(username)) WHERE deleted = 0;
   CREATE UNIQUE INDEX uk_system_users_mobile   ON system_users (mobile) WHERE deleted = 0 AND mobile IS NOT NULL AND mobile <> '';
   CREATE UNIQUE INDEX uk_system_users_email    ON system_users (email)  WHERE deleted = 0 AND email  IS NOT NULL AND email  <> '';
   DROP INDEX IF EXISTS idx_system_users_01;  -- username，被 uk_system_users_username 取代（MyBatis-Plus 查询恒带 deleted=0）
   DROP INDEX IF EXISTS idx_system_users_02;  -- mobile，被 uk_system_users_mobile 取代
   DROP INDEX IF EXISTS idx_system_users_03;  -- email，被 uk_system_users_email 取代
   ```
   保留 `idx_system_users_04 (dept_id)`。username 用 `lower()` 表达式索引：即便应用层漏规范化，DB 仍按小写强制唯一（纵深防御）。
   - **空串处理**：email/mobile 列 `DEFAULT ''`，故必须 `<> ''` 排除，否则多个空串撞索引（M3「NULL 允许多个」的真实语义是「无值允许多个」，空串=无值）。

### D2 应用层规范化与登录兼容（`AdminUserServiceImpl`）
- 新增私有 `normalizeUsername(String)`：`StrUtil.isBlank` 原样返回，否则 `username.trim().toLowerCase(Locale.ROOT)`。
- 写入路径规范化：`createUser`、`updateUser`（含 username 变更）、`importUser` 持久化前对 username 调 `normalizeUsername`。
- **登录兼容（M2 关键）**：`getUserByUsername`（L374，登录/校验入口）查询前对入参同样 `normalizeUsername`，保证存量清洗为小写后登录名匹配不断链。种子 `admin` 已小写，无破坏。
- 保留 `validateUsernameUnique/Mobile/Email` 作为友好前置提示（§3.3），不删除。

### D3 DB 冲突 → 稳定错误码映射（最终防线）
- 在 `createUser` / `updateUser` / `importUser` 的持久化调用外层 `catch (DuplicateKeyException e)`（Spring 对 PG 23505 的转译，代码库既有范式），按异常消息中的约束名分派：
  - `uk_system_users_username` → `USER_USERNAME_EXISTS`（1_002_003_000）
  - `uk_system_users_mobile` → `USER_MOBILE_EXISTS`（1_002_003_001）
  - `uk_system_users_email` → `USER_EMAIL_EXISTS`（1_002_003_002）
  - 无法辨识约束名 → 保守抛 `USER_USERNAME_EXISTS` 并记 WARN（不吞异常、不回退成功）
- 转译后抛 `ServiceException`，事务随之回滚（PG 23505 已中止事务，无需保存点续用，因不再于同事务内继续查询）。

## 7. 交付偏差登记（2026-09-20 实施后回填，以 codex 评审为准）

本节记录实施与初版计划的已批准偏差，权威交付内容以 docs/05 ZS-DB-010 卡片开发记录与 [codex-ZS-DB-010 台账](../../docs/reviews/codex-ZS-DB-010.md) 为准。

1. **D1 索引保留（推翻原 DROP）**：原计划 D1 第 3 段 `DROP INDEX idx_system_users_01/02/03`，实施改为**保留**。codex r0 P2 指出 `lower()` 表达式索引与部分唯一索引（带 `WHERE deleted=0`）服务不了 `WHERE col = ?` 等值查询（MyBatis-Plus 既有查询路径依赖），删除会造成等值查询无可用索引。唯一性由新增三个部分唯一索引承担，idx_01/02/03 保留为查询路径。PG 验证 P1 断言随之改为「三唯一索引存在且 partial + idx_01/02/03 保留（=3）+ idx_04 保留」。
2. **D3 约束名精确提取（codex r1 P2 强化）**：原 D3 按「异常消息中的约束名分派」，实施用正则 `unique constraint "([^"]+)"` 精确提取约束名后 `equals` 比对，而非 `contains` 子串匹配——避免 PG DETAIL 回显的冲突值（如邮箱 `uk_system_users_mobile@example.com`）被误判为 mobile 约束。
3. **D3 覆盖面扩展（codex r0 P1/P2）**：除 createUser/updateUser/importUser 外，`updateUserProfile` 亦接入 translateDuplicateKey（跨租户改资料越租户内预检）；`importUserList` 两个 catch 改 rethrow（PG 事务撞 23505 后已 abort 25P02，续查会假报成功）。
4. **R2 真并发强化（codex r0/r1 P2）**：P0/P3 由 `spawnSync` 顺序插入改为异步双会话重叠事务——A `BEGIN;INSERT;pg_sleep;COMMIT` 持锁，轮询 `pg_stat_activity` 确认 A active 后起 B，每进程独立完成计时（避免 B 耗时含等待 A 而伪证重叠）。
