# 运行监控与告警响应（Outbox 队列/依赖）

> 交付批次：**ZS-OPS-002.B**（验收批次 B05）。上游依赖：ZS-JOB-004（Outbox 健康监测 + 恢复控制台）、ZS-OPS-002.A（部署模板）、ZS-DB-005。
> 适用范围：`zszj-module-infra` Outbox 事件队列（`outbox_event` / `dispatcher_lease`）及其依赖（数据库、Redis）。
> **本说明只描述「已启用」的监测与告警能力；未接入的外部告警系统 / 容量实测 / 备份恢复演练见文末「边界声明」。**

---

## 1. 概述

ZS-JOB-004 已落地 Outbox 健康监测器 `OutboxHealthMonitor`（聚合积压 / DEAD / 最长等待 / 失败率 / 过期租约 → 越阈清单 `breaches`），但仅能通过管理端点 **按需拉取**——无人查询则越阈静默。

ZS-OPS-002.B 在此基础上补齐 **主动发现** 能力，使「依赖故障和积压被发现、失败不静默」：

| 组件 | 类型 | 职责 |
| --- | --- | --- |
| `OutboxHealthAlertScheduler` | `@Scheduled` 周期探针 | 按 `infra.outbox.health.alert.interval-ms` 周期拉取快照，把越阈 **分级告警** 到日志（供采集/告警系统消费） |
| `OutboxQueueHealthIndicator` | Actuator `HealthIndicator`（贡献者名 `outboxQueue`） | 把越阈快照映射为 `/actuator/health` 健康态，供编排器/监测组消费 |

两者都是 `OutboxHealthMonitor` 的 **纯消费者**——越阈计算逻辑与阈值全部来自 JOB-004，OPS-002.B **不新造阈值、不改判定规则**。

## 2. 已启用告警清单

告警门控：`infra.outbox.health.alert.enabled=true`（默认启用）。关闭后 `OutboxHealthAlertScheduler` 不装配、不产任何调度开销；`OutboxQueueHealthIndicator` 仍随 Actuator 常驻。

| 越阈码 | 触发条件（JOB-004 判定） | 探针告警级别 | 健康态 |
| --- | --- | --- | --- |
| `PENDING_BACKLOG_CRITICAL` | PENDING 积压 > `backlog-critical`（默认 5000） | **ERROR（严重）** | DOWN |
| `DEAD_EVENTS_PRESENT` | 存在 DEAD 事件（连续失败达上限，需人工恢复） | **ERROR（严重）** | DOWN |
| `STALE_LEASE_PRESENT` | 存在过期租约（dispatcher 停摆征兆） | **ERROR（严重）** | DOWN |
| `PENDING_BACKLOG_WARN` | PENDING 积压 > `backlog-warn`（默认 1000） | WARN（预警） | DOWN |
| `LONGEST_WAIT_WARN` | 最老 PENDING 等待 > `longest-wait-warn-seconds`（默认 3600） | WARN（预警） | DOWN |
| `FAILURE_RATE_WARN` | 失败率 > `failure-rate-warn-percent`（默认 5%） | WARN（预警） | DOWN |

**分级规则**：越阈清单含任一「严重级」码 → 整轮探针按 **ERROR** 告警（取最高严重度，不漏报严重项）；仅含「预警级」码 → **WARN**；未知码（JOB-004 未来新增且未列入严重集合）→ 保守降级为 **WARN**（不误升级为 ERROR）；清单为空 → 不产告警噪声。

## 3. 越阈码 → 响应动作

告警日志格式：`[probe][Outbox 队列告警(严重/预警) breaches=[...] pendingBacklog=.. deadCount=.. longestWaitSeconds=.. failureRatePercent=.. staleLeaseCount=..]`。运维据此定位后，走 JOB-004 恢复控制台处置（管理端点，需相应权限）：

| 越阈码 | 首选响应动作 | 端点 / 权限 |
| --- | --- | --- |
| `DEAD_EVENTS_PRESENT` | 查列表定位 DEAD → 看详情判因 → 修复下游后重试，或确认无效后跳过 | `GET /infra/outbox-event/page`、`GET /infra/outbox-event/get-detail`（`infra:job:query`）→ `PUT /infra/outbox-event/retry` / `PUT /infra/outbox-event/skip`（`infra:job:recover`） |
| `PENDING_BACKLOG_CRITICAL` / `_WARN` | 核查 dispatcher 是否在跑（见 `STALE_LEASE_PRESENT`）、下游是否阻塞；必要时扩容消费端 | 同上（page/get-detail 观测积压趋势） |
| `STALE_LEASE_PRESENT` | dispatcher 停摆征兆：核查调度线程/实例存活，参考《定时任务启停手册》恢复派发 | 运维排查（非本模块端点） |
| `LONGEST_WAIT_WARN` | 检查退避/重试是否卡住、`next_retry_at` 是否长期不推进 | `GET /infra/outbox-event/page`（按等待时长排序观测） |
| `FAILURE_RATE_WARN` | 失败率抬升：抽样 get-detail 看失败原因聚类，判断是下游故障还是数据问题 | `GET /infra/outbox-event/get-detail` |

> 人工重试受 `infra.outbox.health.max-manual-retry`（默认 3）护栏约束，超限即拒绝（防无限重试）。
> 按需健康快照亦可经 `GET /infra/outbox-event/health`（`infra:job:query`）主动拉取。

## 4. 健康端点与组边界（liveness 纯净红线 + 匿名详情不外泄）

Actuator 健康端点配置（`application.yaml` → `management.endpoint.health`）：

| 端点 / 组 | 包含贡献者 | 详情可见性 | 用途 |
| --- | --- | --- | --- |
| `/actuator/health`（聚合） | 全部（含 `outboxQueue`、`db`、`redis`、`ping` …） | 仅状态（默认 `never`） | 总体健康观测 |
| `/actuator/health/monitoring` | `outboxQueue,db,redis,ping` | **仅状态（`show-details: never`）** | **专用监测组**：队列 + 依赖的状态聚合视图，供采集/告警系统轮询「是否越阈/依赖故障」 |
| `/actuator/health/liveness` | **仅** `livenessState`（Spring Boot 默认） | — | 存活探针（编排器重启判据） |
| `/actuator/health/readiness` | **仅** `readinessState`（Spring Boot 默认） | — | 就绪探针（流量接入判据） |

> **匿名安全边界（codex r0 P1）**：`/actuator/health` 与 `/actuator/health/**` 对匿名放行（ZS-ENG-005 健康探针需要），
> 因此**任何**健康端点都**不对匿名开放组件详情**——内建 `db`/`redis` 指示器详情含依赖异常原文与内部地址，属敏感信息。
> 匿名监控面只暴露**状态**：队列越阈或依赖故障 → 聚合 health 与 `monitoring` 组状态 DOWN（被发现）。
> **越阈码 / 指标详情经两条非匿名通道获取**：①探针结构化日志（ERROR/WARN 携越阈码与关键指标）；
> ②授权端点 `GET /infra/outbox-event/health`（`infra:job:query`）。经 HTTP 携详情的授权监控面归后置外部接入（B11/D-10）。

> **铁律（不可违反）**：`outboxQueue` **绝不** 纳入 `liveness` 组。
> 队列积压 / DEAD 是 **可恢复的运维信号**，而非进程失活。若将其计入 liveness，编排器（K8s / docker healthcheck）会在积压时判定实例「不存活」并重启——重启不消化积压，反而中断在途派发，形成 **越积压越重启的重启风暴**。因此积压只影响聚合健康与 `monitoring` 组（供告警），**永不** 影响 liveness。
>
> `OutboxQueueHealthIndicator` 在探针失败（依赖不可用）时返回 **DOWN + `reason=MONITOR_PROBE_FAILED`**，**绝不** 伪装 UP（失败不静默）；指示器 details 仅含指标值、越阈码与异常 **类名**，不含 payload 与异常原文（脱敏）；探针失败日志**只记异常类名**，不渲染异常对象（消息/堆栈/cause 链可能携内部地址/凭据）。

## 6. 依赖故障处置

`OutboxHealthMonitor.snapshot()` 依赖数据库（聚合 `outbox_event` / `dispatcher_lease`）。当依赖不可用：

- **探针路径**（`OutboxHealthAlertScheduler`）：捕获异常 → **ERROR** 日志 `[probe][Outbox 健康监测探针失败，依赖可能不可用 errorClass=..]`，异常就地隔离 **不击穿 `@Scheduled` 调度线程**（否则后续轮次永久静默）；依赖恢复后下一轮自动恢复监测。
- **健康端点路径**（`OutboxQueueHealthIndicator`）：返回 **DOWN + `MONITOR_PROBE_FAILED` + 异常类名**，使 `/actuator/health` 与 `monitoring` 组如实反映「监测能力本身不可用」。
- 数据库 / Redis 自身的健康由 Actuator 内建 `db` / `redis` 贡献者反映，已纳入 `monitoring` 组一并观测。

> 「失败不静默」三层含义：①探针异常不吞（必产 ERROR）②越阈必告警（不静默）③调度线程不被击穿（后续轮次不失能）。
