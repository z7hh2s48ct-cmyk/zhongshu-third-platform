# 查询索引、批量更新保护与并发使用规范评审（ZS-DB-020）

> 评审日期：2026-09-09。基线：ZS-DB-008 事务与锁回归完成后。
> 性质：静态评审 + 本地可执行验证项登记；PG 执行计划（EXPLAIN ANALYZE）实测与数据规模指标待 B02 环境按第 5 节补证。

## 1. 全表更新/删除防护（BlockAttackInnerInterceptor）

现状：[ZszjMybatisAutoConfiguration](../zszj-framework/zszj-spring-boot-starter-mybatis/src/main/java/cn/zszj/framework/mybatis/config/ZszjMybatisAutoConfiguration.java) 中 `BlockAttackInnerInterceptor` 处于注释状态——不带 WHERE 的全表 UPDATE/DELETE 不会被框架拦截。

评审结论：

- **不全量开启**。该拦截器会误伤合法场景（如按主键的全量字段更新虽不受影响，但空条件的批处理用法需要逐 Mapper 排查），开启属于行为变更，必须以回归结果决策（05 文档同此判断）。
- **替代防护（本评审采用）**：全表写操作只允许出现在获批的专用路径（定时清理 Job、Flyway 迁移）；业务 Mapper 新增无 WHERE 的更新/删除在代码评审中按缺陷处理。是否开启拦截器留待 B02 以回归对比决策。
- 已有受控批量删除路径：访问/错误/任务日志与 OAuth2 Token 清理均已改为有界删除（ZS-DB-011~015，主键集限定 + LIMIT），并经真实 PG 验证（两轮清空 5 行过期、单轮 ≤3）。

## 2. 乐观锁与并发控制

现状：框架未注册 `OptimisticLockerInnerInterceptor`，DO 无 `@Version` 字段；并发控制依赖：唯一约束（数据库层兜底）、`FOR UPDATE`（`BaseMapperX` 行锁）、事务边界。

评审结论：

- **不引入全局版本字段**（05 文档："不代表应给全部表添加版本号"）。
- 按场景分派的并发机制规范：

| 场景 | 机制 |
|---|---|
| 单行读-改-写且存在并发覆盖风险 | 事务 + `FOR UPDATE`（ZS-DB-008 已验证锁与超时行为可预测） |
| 业务键唯一（账号、字典编码等） | 数据库唯一约束 + 稳定错误码（字典部分唯一索引已落地 ZS-CFG-002.A；账号唯一性 D-09 批准后由 ZS-DB-010 落地） |
| 计数累加类 | 原子 UPDATE（`SET x = x + 1`），禁止读-改-写 |
| 跨聚合一致性 | 事务边界内完成；Redis/外部消息的同步回滚不等同数据库回滚（B05 Outbox 承接） |

- 已有冲突测试：序列并发（ZS-DB-006 C4）、行锁超时（ZS-DB-008 C4）、字典并发唯一（ZS-CFG-002.A C3）。

## 3. 查询索引评审（基于 V1 基线结构）

V1 基线已含上游导出的全部二级索引；以下为需要 B02 以 `EXPLAIN ANALYZE` 复核的点（不在本评审预设结论）：

1. 高频过滤列的索引覆盖：`system_users.username`、`system_user_role.user_id/role_id`、`system_role_menu.role_id/menu_id`、`system_dict_data.dict_type`、各日志表 `create_time`（有界删除的子查询按时间扫描，见 ZS-DB-011~015）。
2. 字典唯一索引（ZS-CFG-002.A 新增部分唯一索引）仅影响写路径校验，不影响读路径。
3. 索引新增一律以 V2+ 增量迁移交付（禁止改写 V1 基线），并用真实数据量验证执行计划。
