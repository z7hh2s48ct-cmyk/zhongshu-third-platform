# 数据库升级与恢复规程（ZS-DB-005）

> 冻结日期：2026-09-09。前置：[数据库迁移规范](数据库迁移规范.md)（ZS-DB-003）、[数据库环境方案](数据库环境方案.md)（ZS-DB-002）、V1 基线与 V2 回填迁移（ZS-DB-004/005）。
> 本规程的演练记录见第 5 节（2026-09-09 于一次性 PG17 容器实测）。

## 1. 迁移编写规则（有序与可逆边界）

1. 每个迁移文件头部必须注释声明：**目的 / 是否可逆 / 不可逆时的前向修复步骤 / 数据影响**。
2. 结构变更顺序规范：加可空列 → 回填（分批 UPDATE）→ 加约束/默认值；禁止在同一迁移里直接加非空列。
3. 破坏性变更（DROP COLUMN/TABLE、收窄类型、删数据）必须在文件头显式标注"不可逆"，并在执行前完成备份（第 4 节）；禁止无备份的破坏性迁移提交。
4. 回填脚本必须分批（按 id 区间）并可中断续跑（WHERE 条件幂等）。
5. 涉及既有初始化库（旧 dump 手工建的库）的迁移一律幂等写法（`IF NOT EXISTS` 等，参照 V2 qrtz 回填）。

## 2. 既有库接管（禁止盲目 baseline）

以旧 dump 手工建的库接入 Flyway：

1. **先核对再接管**：对比该库与 V1 基线的结构（表/列/序列清单），差异必须逐项登记；
2. 接管 = 该库首次以 `ZSZJ_FLYWAY_ENABLED=true` 连接，`baseline-on-migrate` 按基线版本 `20260909.001` 建立标记，V1 不重放；
3. 结构差异以版本号大于基线的**显式差异迁移**表达（如 V2 qrtz 回填），不允许依赖"到时候手工补"；
4. 接管后立即执行第 4 节备份，记录接管时点与历史表内容（`flyway_schema_history` 查询结果存档）。

## 3. 失败语义与中断恢复

- **唯一权威执行入口是应用启动（Flyway）**：`validate-on-migrate` 失败（脚本被篡改）或迁移执行失败，应用拒绝启动——失败不会被伪报为成功。
- **手工执行迁移 SQL 仅允许在事务包裹下**进行预演（`BEGIN; ... ROLLBACK;`）。实测（2026-09-09 演练）：自动提交模式下迁移中途失败会残留半套变更；事务包裹模式下完全回滚、零残留。Flyway 每个迁移独立事务，等价于事务包裹语义。
- 中断恢复步骤：修复失败原因 → 处理半套变更（事务模式无需处理；若发生了非事务 DDL 中断，按文件头的"前向修复"步骤手工对齐）→ `flyway repair` 仅限在确认历史表失配原因后由负责人执行 → 重启应用重放该版本。

## 4. 备份与恢复

1. 时机：任何含破坏性变更的迁移执行前，必须对目标库 `pg_dump -Fc` 完整备份（模板见 [数据库环境方案](数据库环境方案.md) 第 4 节）。
2. 恢复：`pg_restore -d <新临时库>`，先在临时库比对核心表行数与关键种子，再切换。
3. 演练：每次 B02/B11 保障活动前重跑第 5 节演练脚本化步骤；实测 RPO/RTO 回填 [数据库环境方案](数据库环境方案.md)。
4. 禁止用"删库重建"冒充升级验收；不承诺所有变更可无损回滚——不可逆变更只能前向修复。
