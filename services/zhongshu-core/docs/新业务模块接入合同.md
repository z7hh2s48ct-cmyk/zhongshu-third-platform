# 新业务模块接入合同（ZS-BPM-004）

> 文档日期：2026-09-25（ZS-BPM-004 交付物·技术准备沉淀件）
> 上位依据：[05-任务清单](../../../docs/05-底座模块分析与开发任务清单.md) ZS-BPM-004 卡、[03-开发顺序与验收标准](../../../docs/03-底座二次开发顺序与验收标准.md) B09、[02-需求台账](../../../docs/02-一期底座需求规格与待决策台账.md) §6.5（D-07 确认前只允许中性技术夹具，禁止固化业务字段/状态）
> 可执行参照：`../zszj-module-bpm/src/test/java/cn/zszj/module/bpm/contract/TechNeutralContractSample.java`（测试作用域中性样例，配套 `TechNeutralContractSampleTest` 11 用例端到端验证提交→审计→事件→待办完整链路）
> 适用范围：新业务模块（含外部系统接入）在启用前逐项回填本合同的执行状态并验收；本件为技术准备沉淀，**不因样例通过而豁免**真实系统接入的逐系统回填与 UAT（见 §5）。

## 0. 使用方式

1. 每个新模块/新系统立项时复制 §1 的 12 项条款，逐项回填「执行状态（已满足/不适用/待补）」与证据位置（代码位置、测试、验收记录）；
2. §1 各项中标注「样例演示」者为 ZS-BPM-004 中性样例中可运行的对照实现——先读样例再写业务代码，**只做法条迁移，不复制样例的常量与载荷**；
3. 回填完成前不得进入联调；D-07 批准前不得固化任何业务字段、状态机与组织语义。

## 1. 十二项接入合同

### 1.1 模块注册

- **要求**：源码存在 ≠ 模块启用。启用一个模块须完成六步规程：① 根 pom `modules` 取消注释 + ② `zszj-server` 依赖引入 + ③ `ModuleCatalog` 清单迁移（DISABLED → ENABLED）+ ④ `DefaultController` 移除对应兜底 + ⑤ V1 后追加该模块菜单的增量迁移 + ⑥ 两道检查通过。任何一步缺失都会被检查拦截。
- **对接点**：`zszj-framework/zszj-common/.../catalog/ModuleCatalog.java`；`scripts/eng/verify-module-whitelist.mjs`；`ModuleWhitelistTest`；[功能目录](功能目录.md)。
- **验收方式**：ModuleWhitelistTest 与 verify-module-whitelist.mjs 双通过；模块关闭态请求命中 501 兜底且无业务写入。

### 1.2 API / DTO

- **要求**：对外接口挂模块专属前缀（`/admin-api/{模块}/**`）；对外 DTO 独立定义，不得直接暴露 DO；匿名访问必须显式登记白名单，白名单外全部鉴权；错误码按模块段分配并登记矩阵，禁止跨段占用。
- **对接点**：[接口清单与匿名白名单](接口清单与匿名白名单.md)、[错误响应与状态码矩阵](错误响应与状态码矩阵.md)、各模块 `enums/ErrorCodeConstants`。
- **验收方式**：接口清单逐项回填（含鉴权要求）；错误码矩阵核对无冲突；白名单外直调返回未授权。

### 1.3 对象归属

- **要求**：写侧入口必须持显式租户上下文，缺失即拒——**不默认 0、不伪造归属**；读写按租户过滤；跨租户对象不可见、不可改（0 行即拒而非静默成功）；忽略租户只能显式且受控使用。
- **对接点**：`TenantContextHolder` / `TenantUtils`；设施层强制先例：`JdbcReliableEventPort`（租户缺失即拒）、`NotifyTodoServiceImpl#requireTenant`、`JdbcAuditPort`（`tenantId` 可空但不默认 0，属 D-09 扩展点）。
- **验收方式**：新模块同型用例（无租户写侧拒绝、跨租户 0 行拒绝且拒绝留痕）；样例演示：`TechNeutralContractSampleTest` 用例⑥⑧。

### 1.4 版本并发

- **要求**：业务对象提供单调递增版本号；一切更新携带编辑时的 `expectedVersion`，0 行即冲突——拒绝（DENIED 留痕，走独立事务）并抛出，**不得静默覆盖他人更新**；跨进程事件必须携带 `bizVersion`；消费侧以版本水位护栏拒绝乱序旧版本（不复活、不回退水位）。
- **对接点**：样例 `TechNeutralContractSample#complete`；待办版本护栏 `system_notify_todo.biz_version`（单调）；Inbox 水位 `JdbcConsumerInboxPort`（`staleVersion()`，水位同一事务 RAISE）。
- **验收方式**：样例演示：用例④（绕过版本拒绝 + 无副作用）、用例⑤（终态守卫重复完成拒绝）、用例⑥（乱序旧版本事件水位拒绝）；新模块同型用例。

### 1.5 引用历史

- **要求**：跨模块引用采用**来源快照**而非活引用——记录引用时点的归属（组织/人员/账号映射），被引用对象后续变更或人员任职变动（IAM-004）**不追改历史**；历史查询须能按"当时归属"解释；对象删除采用逻辑删除，历史引用保持可解析。
- **对接点**：[数据权限授权矩阵](数据权限授权矩阵.md)、[跨组织访问授权矩阵](跨组织访问授权矩阵.md)、IAM 任职生命周期与历史归属迁移设施。
- **验收方式**：新模块对历史引用做归属快照测试（如组织变更后历史记录归属不漂移）；引用变更（增/删/换）逐次留审计（见 §1.7）。

### 1.6 动作与字段权限

- **要求**：每个写动作声明动作级权限串（`模块:资源:动作`，`@PreAuthorize("@ss.hasPermission(...)")`）；动作权限之外，对象级资格（参与人/归属）在服务层二次校验——两层不可互相替代；跨组织访问一律走显式授权（CrossOrgVisit），不得以"同租户"代替；敏感字段按字段级脱敏输出。
- **对接点**：`@ss.hasPermission` 注解模式（各 Controller）；`CrossOrgVisitApi` / `CrossOrgVisitService` / `CrossOrgVisitScopeHolder`；[数据权限授权矩阵](数据权限授权矩阵.md)、[跨组织访问授权矩阵](跨组织访问授权矩阵.md)。
- **验收方式**：权限矩阵逐接口回填；无注解写入口为零（或登记豁免并说明）；跨组织访问用例（授权前拒绝、授权后放行、撤权后即刻拒绝）。

### 1.7 审计

- **要求**：每个业务动作必留审计：SUCCESS 随业务事务（业务回滚则审计不留，fail-closed 防"无成功审计而提交"）；DENIED / FAILURE 走独立事务（业务回滚不丢失留痕）；`eventType / actorType / result` 必填缺失即拒；携对象版本基线（`bizVersion`）；幂等键防重复入账；明细落库前脱敏（不可改写历史）。
- **对接点**：`AuditPort` / `JdbcAuditPort`（事务语义见 §4）、`AuditEventTypes` 目录、[日志脱敏策略](日志脱敏策略.md)。
- **验收方式**：样例演示：用例①（SUCCESS 随事务 + 版本基线）、用例④（DENIED 独立留痕且业务回滚不丢）；新模块动作清单 × 审计事件类型对照表回填。

### 1.8 Outbox（可靠事件）

- **要求**：一切跨进程 / 跨系统通知**一律**以 Outbox 事件预写实现：与业务数据**同事务**追加（MANDATORY——无真实事务即拒绝，不得循环外异步补写）；租户缺失即拒；载荷自包含（消费方不得依赖回读生产库复原语义）；投递是 at-least-once，消费幂等由 Inbox 吸收；禁止绕过领取/确认机制私自投递确认。
- **对接点**：`ReliableEventPort` / `JdbcReliableEventPort`；`OutboxDispatcherService`（领取/确认；**注意：其投递路径不提供事务**，接线方须以编程式事务包裹消费侧投递——见 §5 与 D-07 登记）；`JdbcConsumerInboxPort`（消费幂等 + 版本水位）。
- **验收方式**：样例演示：用例②（同事务预写 + 载荷字段齐备）、⑦（无租户追加拒绝）、③⑩（投递确认 + Inbox 幂等重投吸收）；新模块事件清单（eventType / 载荷模式 / 消费方）回填。

### 1.9 待办

- **要求**：任务型事项登记待办（幂等键 `(租户, sourceType, todoKey)`，重复注册返回既有）；流转**只经事件驱动**（Outbox → Sink → `applyTransition`，Inbox 幂等）——禁止业务侧直改待办状态形成双写；服务侧终态守卫与 `biz_version` 单调护栏不得绕过；待办状态与业务状态通过事件最终一致，不做跨库强一致承诺。
- **对接点**：`NotifyTodoService` / `NotifyTodoRegisterCmd` / `NotifyTodoEventSink`（`NOTIFY_TODO_TRANSITION`）/ `NotifyTodoTransitionCmd`。
- **验收方式**：样例演示：用例①（注册幂等基座）、⑨（同键幂等返回既有）、②③（事件驱动推进至 COMPLETED）；新模块待办清单（todoKey 生成规则 / sourceType / 收件人）回填。

### 1.10 私有文件

- **要求**：私有文件禁止直链与存储 URL 外泄；下载/导出走**票据交付**：签发一次性票据（服务端只存散列）→ 原子兑换建立会话（绑定主体/会话/资产版本/用途）→ 逐块鉴权取流、每块重检（撤权后停止输出）；文件上传登记归属与用途；孤儿对象由清理机制回收。
- **对接点**：`FileApi`；`FileDeliveryService`（ZS-FILE-004.A 票据交付）/ `FileOrphanService`（ZS-FILE-005.B 孤儿清理）。
- **验收方式**：文件引用（fileId 归属、用途、引用方）逐项登记；票据交付既有测试套件通过；新模块不得自建文件下载通道。

### 1.11 流程适配

- **要求**：需要审批流的模块**不得自建状态机双写**——流程引擎表（`ACT_*`）由引擎 schema 管理器自管（禁止手写 DDL / Flyway 接管），模块业务扩展表走 Flyway 版本化迁移，责任严格分离；流程动作（发起/通过/拒绝/撤回/转办）经事件（Outbox → Sink → 待办）同步到业务侧；启用 BPM 走 §1.1 六步规程。
- **对接点**：[BPM引擎表与业务扩展表迁移责任决策](BPM引擎表与业务扩展表迁移责任决策.md)；`NotifyTodoEventSink`（流程动作 → 待办流转事件）；ZS-BPM-002（审批资格与对象授权校验）。
- **验收方式**：逐流程回填"流程动作 ↔ 业务事件 ↔ 待办"映射表；D-07 批准后的首链接线（dispatcher 投递路径编程式事务包裹）作为首个联验项。

### 1.12 跨系统声明

- **要求**：接入外部系统前逐项书面声明：① **权威对象**——每个共享对象明确唯一 source of truth 与写入方向；② **来源 ID 与账号映射**——外部 ID ↔ 内部 ID 的稳定映射（含映射变更史），账号映射到内部主体（禁止以姓名/手机号等可变属性充当键）；③ **契约版本及回退**——接口/消息契约的版本号、兼容窗口与回退/降级路径（回退不得破坏已确认的幂等与版本语义）。
- **对接点**：[Token传输与连接凭据规范](Token传输与连接凭据规范.md)；样例的 `todoKey`（稳定业务键）+ `TODO_SOURCE_TYPE`（来源标识）演示来源映射的幂等键组合。
- **验收方式**：逐系统一表回填（权威对象 / ID 映射表 / 契约版本 / 回退路径）+ 对应 UAT；变更映射或契约版本须走变更记录。

## 2. 同事务内部事件与跨进程事件的边界

| 维度 | 同事务内部事件（进程内） | 跨进程事件（Outbox） |
|---|---|---|
| 载体 | Spring `@EventListener`（同步） | `outbox_event` 表 + Sink |
| 事务 | 监听发生在发布方事务内（样例直证） | 与业务同事务预写（MANDATORY） |
| 副作用 | 仅进程内扩展；不落库、不跨进程、随事务回滚不发生 | 落库、可投递跨进程；at-least-once + Inbox 幂等 |
| 适用 | 同事务内的解耦扩展（缓存失效、派生计算） | 一切跨进程 / 跨系统通知、待办流转 |

**判定法则**：需要跨进程、需要投递保证、需要消费幂等 → 一律 Outbox；不需要出进程且必须与发布方同生共死 → 可内部事件。样例演示：`TechNeutralContractCreatedEvent`（内部）与 `NOTIFY_TODO_TRANSITION`（跨进程）的分工。

## 3. 不为未来域预建业务表（约束）

- 接入合同沉淀阶段**禁止为未立项业务域预建业务表、字段与状态机**；测试/演示对象表只允许技术语义字段（样例表 `tech_neutral_contract_record` 为参照：key/status(PENDING|DONE)/version/租户列，无任何业务态）。
- 依据：docs/02 §6.5（D-07 确认前允许 PG 适配与中性技术夹具、**禁止固化业务字段/状态**）；docs/05 ZS-BPM-004「不为未来域预建业务表」。
- 验收方式：评审检查新增表/字段是否含业务域名词与业务状态枚举；确认后入库。

## 4. 事务语义总表（B03~B05 设施实测口径）

| 设施 | 传播行为 | 语义要点 |
|---|---|---|
| `AuditPort.record`（SUCCESS） | REQUIRED | 随调用方事务；校验/写入失败先标记所参与事务 rollback-only 再抛出（fail-closed） |
| `AuditPort.record`（DENIED / FAILURE） | REQUIRES_NEW | 独立提交；业务回滚不丢失留痕；其失败不牵连业务事务 |
| `ReliableEventPort.append` | MANDATORY | 无真实事务即拒（fail-closed）；租户缺失即拒 |
| `ConsumerInboxPort.tryBegin` | MANDATORY | 无事务即拒；保存点抢位；版本水位在同一事务内 RAISE |
| `Sink.deliver`（消费侧投递） | 调用方事务 | 生产由接线方负责包裹：**dispatcher 投递路径不提供事务，须编程式事务包裹**（D-07 首链接线任务） |

## 5. 与 D-07 的关系与红线

- 本件为 B09「技术准备」沉淀：12 项条款在 D-07 批准后**逐系统回填 + UAT**，中性样例通过**不等于**任何业务系统可用；
- 中性红线：样例与夹具的常量、载荷、状态只含技术语义（`PENDING`/`DONE`/version/key），无试点业务态（加盟商/线索/审批业务态等）；真实接入时逐系统替换，并回填契约版本与回退路径；
- 首链接线事项：`OutboxDispatcherService` 投递路径与消费侧事务包裹的核实（已由 `NotifyTodoEventSink` javadoc 登记为 D-07 首链接线任务）。
