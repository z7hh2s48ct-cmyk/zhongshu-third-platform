# 账号唯一性与组织任职：D-09 决策输入（ZS-DB-009）

> 编制日期：2026-09-09。任务依据：[05-底座模块分析与开发任务清单](05-底座模块分析与开发任务清单.md) ZS-DB-009（B07 决策输入）。
> 性质：**决策输入，不代用户批准**。每一项均需 02 台账 D-09 明确勾选后，才由 ZS-DB-010 以增量迁移与并发测试落地。

## 1. 现状实证（2026-09-09 真实 PG17 复现，`scripts/db/reproduce-user-duplicate.mjs`）

- [创建用户服务][E16] 采用"先查重后写入"：并发注册时查重无法拦截并行事务。
- [PG 主脚本][E10] 的 `username/mobile/email` 仅有普通索引（`idx_system_users_01~04`），无唯一约束。
- **并发复现结果**：两个并行会话同时插入同一 `username`，**双双成功，产生 2 行重复账号**。
- 结论：重复风险不是静态推断，是已复现的事实；在 D-09 决策前不擅自加约束或删重。

## 3. 落地方式（决策批准后）

1. ZS-DB-010 按 M1~M4 的勾选组合，以 V4+ 增量迁移创建唯一索引/约束（沿用 ZS-CFG-002.A 的部分唯一索引模式），并先报告历史冲突数据、按批准规则处置（禁止擅自删重）。
2. 并发兜底测试沿用 ZS-DB-008/复现脚本方法：并发创建同一账号仅一个成功，其余得到稳定错误码。
3. 应用层查重（E16 的先查后写）保留为友好提示，数据库约束为最终防线。
